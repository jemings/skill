# agent-dispatch -- 범위가 끝날 때까지 grilling, 계약, 구현, 검수, 착륙

너는 **오케스트레이터**다. **실행 범위**(지도 이슈의 sub-issue, 또는 조건 하나에 맞는 이슈 집합) 가운데 지금 착수할 수
있는 이슈 묶음(**frontier**)을 끝까지 가져간다.

1. frontier 를 고른다.
2. 이슈마다 서브에이전트가 스스로 grilling 해 설계 트리를 가져온다.
3. 근거가 답하는 것은 네가 정하고, 사람의 판단이 필요한 것만 한 라운드로 묻는다.
4. 이슈를 계약서로 다시 쓰고 `ready-for-agent` 로 옮긴다.
5. 구현 서브에이전트가 TDD 로 구현해 draft PR 을 넘긴다.
6. 적대적 리뷰어를 띄우고 그동안 기계 검사를 직접 한다.
7. **깨끗하면 네가 바로 넣는다**(`land.sh`). 사람의 병합을 기다리지 않는다.
8. 넣을 때마다 1로 돌아간다. 고를 것도, 진행 중인 것도 없으면 마지막 보고를 하고 멈춘다.

필요한 스킬(mattpocock-skills): `grilling`, `domain-modeling`, `tdd`, `diagnosing-bugs`. 목록에 플러그인 접두어가
붙어 있으면 그 이름(`mattpocock-skills:tdd`)으로 부른다. 서브에이전트가 직접 부른다.

**스크립트**(`${CLAUDE_SKILL_DIR}/scripts/`). 확정적인 일은 손으로 하지 말고 이것으로 한다. 각 스크립트의 `-h` 가
인자와 출력의 정본이다.

| 스크립트 | 하는 일 | 단계 |
|---|---|---|
| `frontier.sh` | 범위 질의 + 담당 필터. 이슈마다 READY/BLOCKED/OTHERS. 막힘은 blocked_by 링크와 본문 맨 앞의 선행 줄 둘 다(본문이면 5열에 사유) | 1, 9 |
| `in-flight.sh` | 다른 세션이 쥐었는지 판정(BUSY/MAYBE/HELD/FREE), claim/release, `--where`, `--peers`, `--agent`(서브에이전트 정체 판정 WORKING/STALLED/UNKNOWN, `--wait` 로 감시) | 0, 1, 5, 6, 7 |
| `pr-check.sh` | PR 모양: 열림, draft(`--draft`), 대상, HEAD 일치, 깨끗한 트리, 충돌, `Closes #N`, 금지 trailer, 금지 경로. 증거 판정: 판정 줄(`--verdict`), 이어 받기(`--carry`/`--may-touch`) -> EVIDENCE OK/RERUN | 7 |
| `temp-tree.sh` | 던져 둘 사본(detached worktree) 만들기와 지우기. 의존성 symlink, 복사, 표식 파일 | 7, 리뷰어, 구현자 |
| `mutate.sh` | 변이 하나를 걸고 시험을 돌린 뒤 되돌린다. KILLED/SURVIVED | 7, 리뷰어 |
| `land.sh` | 기록을 이슈에 남기고, ready, 대상 변경, 병합(저장소 착륙 명령 또는 gh), 스택 앞 층 닫기, 뒷정리. 저장소 명령(검사, 병합 전)이 있으면 착륙 tip(커밋 보존은 rebase 와 커밋 패치 판정, squash 는 base 를 merge 로 합치고 고유 diff 판정), 검사, 병합 전 커밋, base 이동 시 재시도 | 8 |
| `wait-prs.sh` | 사람이 넣어야 하는 PR, 남의 PR 을 지켜본다 | 9 |

## 실행 전반의 원칙

- **한 번에 이슈 하나**(기본): 한 이슈를 착륙까지 가져간 뒤 다음 이슈의 구현을 보낸다. 넣자마자 base 가 바뀌므로 겹치는
  PR 의 따라잡기와 재검수가 생기지 않고, 사용 한도에도 덜 걸린다. 사람이 병렬을 허락하면 계약서가 바꾸는 파일이 겹치지
  않는 이슈만 함께 보낸다. grilling(읽기만 한다)은 frontier 전체를 함께 보내도 된다.
- **놀지 않는다**: 서브에이전트를 기다리는 동안 그 결과에 기대지 않는 일(다음 이슈의 계약, 이슈 등록, 정리)을 한다.
  "결과가 오면 알리겠다"로 턴을 끝내는 것은 남은 일이 정말 전부 그 결과에 걸려 있을 때뿐이고, 무엇이 걸렸는지 한 줄로
  밝힌다.
- **서브에이전트의 알림과 감시**: "자기 백그라운드 일을 기다린다"(백그라운드 대기)는 그것만으로 정상이 아니다. 그
  기다림은 끝날 수 없는 것일 수 있다(떼어 띄운 실행, 참이 될 수 없는 폴링 루프). 살아 있는 프로세스는 일하는 증거가
  아니다. 판정은 흔적(그 agent 의 기록, 기록에 나온 task 출력, worktree 와 scratch 아래 파일)으로 한다.
  - **감시를 건다**: 백그라운드 대기 알림을 받았는데 그 agent 의 감시가 없으면 아래를 `run_in_background` 로 걸고
    진행 목록 그 줄에 `감시 <task id>` 를 적는다. 처음 걸 때는 `--after` 없이 건다. 감시는 agent 마다 하나다.
    `--path` 에는 그 이슈의 worktree 와 scratch(6단계)를 준다. 공용 scratch 는 주지 않는다(네가 쓴 파일로 거짓
    WORKING 이 난다). grilling 처럼 worktree 가 없으면 `--path` 없이 건다.
    ```sh
    bash "${CLAUDE_SKILL_DIR}/scripts/in-flight.sh" --agent <id> --path <worktree> --path <scratch> --wait
    ```
    알림을 받으면 감시와 함께 같은 명령을 `--wait` 없이 한 번 돌려 그 판정 줄을 보고의 근거로 쓴다(알림만 보고
    "기다리는 중"이라고 쓰지 않는다. `STALLED` 면 곧바로 아래 "깨운다"로 간다).
    감시는 흔적이 모두 15분(`--idle-min`) 넘게 그대로면 `STALLED`, 그 id 의 기록이 없거나 판정할 흔적이 없으면(모두
    지금보다 300초 넘게 미래) `UNKNOWN` 을 내고 끝난다. 그래서 하네스가 너를 깨운다. `UNKNOWN` 이면 근거 줄의 이유를
    본다. `기록이 없다` 면 id 를 확인해 고쳐 다시 건다. `판정할 흔적이 없다` 면 감시를 다시 걸지 않고 진행 목록에
    `감시 없음(판정할 흔적 없음)` 으로 적는다(다시 걸면 곧바로 `UNKNOWN` 으로 끝나 되풀이된다). 그 agent 는 알림으로
    기다리고, 다음 알림과 보고 때마다 `--wait` 없이 한 번 판정해 판정이 나오면 그때 다시 건다. `STALLED` 면 아래
    "깨운다"의 차례대로 다시 건다.
    서브에이전트의 리포트가 오면 그 agent 의 감시 task 를 `TaskStop` 하고 `감시 없음` 으로 적는다. 멈춘 task 의 알림은 무시한다. 감시는
    지켜보기(`wait-prs.sh`, 9단계)와 따로 센다.
  - **리포트 뒤의 알림**: 알림 본문으로 가른다. 본문이 `has not reported yet` 이면 위 감시와 판정 규칙을 따른다.
    리포트를 받은 뒤 그 agent 의 본문이 `report was delivered` 이고 `still running` 이면, 판정 없이
    **그 agent id 로 `TaskStop`** 을 리포트마다 한 번 한다(감시 task 의 `TaskStop` 과 다르다).
    `No task found` 는 이미 끝난 것이니 무시한다. 그 리포트 뒤에도 오는 알림은 정보로만 읽는다.
    이어 하기(Fix 등)는 `SendMessage` 가 agent 를 다시 깨우고, 깨어난 agent 의 다음 리포트에서 이 규칙이 새로 시작된다.
    근거: 하네스 알림 본문은 리포트 전이면 `This agent has not reported yet: it is waiting on its own background work`,
    리포트 뒤면 `This agent's report was delivered to you as a message from "<id>"` 에 `stopped with background work of
    its own still running` 이 붙는다(2026-11 로컬 기록 사후 분석).
  - **깨운다**: 감시가 `STALLED` 로 끝나면 이 차례로 한다.
    1. `SendMessage` 를 보내기 **직전에** `date +%s` 로 깨움 시각을 재어 진행 목록 그 줄에 `깨움 <epoch>` 으로 적는다.
       보낸 뒤에 재면 그사이에 온 응답을 놓친다.
    2. `SendMessage` 로 깨운다. 메시지에 근거(기다리는 task 명령, 판정 줄의 가장 늦은 흔적)를 싣고 셋을 시킨다:
       조건이 참이 될 수 없는 기다림은 `TaskStop` 한다, 끝난 결과는 다시 돌리지 않는다, 아직 돌고 있으면 무엇을
       기다리고 언제 끝날지 한 줄로 쓴다.
    3. 감시를 `--after <깨움 epoch>` 로 다시 건다. 정체 나이를 그 시각부터 세므로 이미 낡은 흔적으로 곧바로 끝나지
       않고, 근거 줄에 깨움 뒤의 응답이 나온다.
       ```sh
       bash "${CLAUDE_SKILL_DIR}/scripts/in-flight.sh" --agent <id> --path <worktree> --path <scratch> --after <깨움 epoch> --wait
       ```
    4. 그 감시가 다시 `STALLED` 로 끝나면 근거 줄의 깨움 뒤 응답을 본다. 하네스는 깨우는 메시지도 그 agent 의 기록에
       남기므로 기록이 바뀐 것은 반응이 아니다.
       - `깨움 뒤 응답 없음` 이면(깨워도 반응 없이 정체가 두 번 이어졌다) 옛 agent 를 `TaskStop` 한다(같은 worktree
         에서 둘이 일하면 안 된다). 그다음 6단계의 "원래 서브에이전트가 없다"로 보고 **같은 등급**으로 이어 하기 줄을
         채워 새로 띄우고, 그 줄의 agent id 를 바꾸고 `감시 없음` 으로 적는다. 정체는 등급 절의 올림 계기가 아니다.
         사람에게도 넘기지 않는다(실패 복구는 에이전트 몫).
       - `깨움 뒤 응답 <시각>` 이면 반응한 것이니 1부터 다시 깨운다(상한 없음, `깨움` 을 새 시각으로 고친다).
       - `깨움 뒤 응답 판정 불가(...)` 이면 반응했는지 모르는 것이니 `TaskStop` 하지 않고 1부터 다시 깨운다(모름을
         옛 agent 를 멈출 근거로 쓰지 않는다).
  - **사용 한도, API 오류**: 판정의 근거 줄에 `API 오류` 가 있거나 사용 한도나 API 오류로 멈추면 새로 띄우지 말고,
    풀린 뒤 `SendMessage` 로 "멈춘 자리에서 이어 하라, 끝난 백그라운드 실행의 결과는 다시 돌리지 말라"고 보낸다.
  - 사람이 쉬게 하라면 서브에이전트와 그 감시를 `TaskStop` 한다. 커밋은 worktree 에 남으니 나중에 `SendMessage` 로
    이어 하게 한다.
- **PR 에는 쓰지 않는다**: 너와 서브에이전트는 PR 에 댓글, 리뷰, 답글을 달지 않고 thread 를 resolve 하지 않는다.
  push, draft 전환, 본문 수정, `land.sh` 의 스택 닫기 댓글은 된다. 검증 기록과 결정은 이슈에 남긴다.
- **확정적인 일은 스크립트로**: 같은 손 절차를 두 번째 하려 하면 이 스킬의 스크립트에 있는지 먼저 보고, 없으면 1단계의
  "저장소 도구를 공용화한다"를 따른다.
- **lifecycle 은 이 스킬이 가진다**: 다른 오케스트레이션 모드나 스킬(예: poteto-mode)과 그 모델 규칙이 같은 세션에
  있어도, 서브에이전트 종류, `model`/`effort`, 지시문, PR 상태는 이 스킬을 따른다. setup-pstack 이 쓰는 pstack 모델
  rules 파일(`pstack-models.md`)은 pstack 역할(feature, bug-fix, arena runners 등)의 설정이라 등급 표에 쓰지 않는다.
- **규율 카드**: 일하는 방법(가장 작은 변경, 자료 모양 먼저, 경계 검사, 근본 원인, 검사로 끝나는 단위, 수치 검증)은
  [`references/disciplines.md`](references/disciplines.md) 의 카드 여섯 장이다. 2, 5, 6, 7단계가 쓴다.

## 서브에이전트의 크기 -- model/effort

띄울 때마다 일의 난이도를 매겨 `model`/`effort` 를 넣는다. 기준은 **완료 기준을 한 번에 채우는 가장 낮은 등급**이다.
신호: 범위(파일, 모듈, PR 수), 불확실성(열린 결정, 원인 모를 결함, 동시성, 프로세스 경계), 위험(공개 계약, 저장
데이터, 맞물린 이슈).

| 등급 | 이런 일 | grilling | 적대적 리뷰 | 구현 |
|---|---|---|---|---|
| 가벼움 | 판단할 거리가 거의 없다: 의존성 한 줄, 문구, 이름 바꾸기 | `sonnet`/`medium` | 없음(기계 검사만) | `haiku`/`max` |
| 보통 | 한 모듈 안의 정해진 변경, 원인이 밝혀진 결함, 시험 더하기, 의미를 살려야 하는 충돌 해소 | `sonnet`/`high` | `sonnet`/`high` | `sonnet`/`medium` |
| 무거움 | 여러 모듈의 구조 변경, 여러 PR, 원인 모를 결함, 동시성, 상태, 프로세스 경계, 맞물린 계약 | `opus`/`xhigh` | `opus`/`high` | `opus`/`high` |
| 아주 무거움 | 무거움에 더해 되돌리기 어렵거나(저장 데이터, 공개 계약) 근거끼리 어긋난다 | `opus`/`max` | `opus`/`xhigh` | `opus`/`xhigh` |

- **가벼움 구현은 `haiku`/`max` 다.** 지시문에 바꿀 자리와 완료 기준을 빠짐없이 적고 "계약서에 없는 판단이 필요하면
  멈추고 보고하라"를 넣는다. 멈추면 한 칸 올려(보통) 다시 보낸다.
- 가벼움 구현 밖에서 판단이 드는 일의 하한은 `sonnet`/`medium` 이다. 이 스킬이나 서브에이전트 크기를 직접 가리키는 사용자, 저장소 규칙이
  정하면 그것을 따른다(pstack 모델 rules 파일은 여기 들지 않는다 -- "실행 전반의 원칙").
- **한 칸 올려 다시 보낸다**: 난이도로 멈췄다, 리포트에 틀린 주장이 여럿이다, 완료 기준을 못 채웠다, 검수에서
  되돌려도 같은 지적이 풀리지 않는다고 판단했다. `SendMessage` 로는 등급을 바꿀 수 없으니 새로 띄우고 이어 하기 줄(6단계)을 채운다. 그 줄의
  `Failed premise` 칸에(grilling 이면 grill-brief 의 한 칸 올린 grilling 줄에) **실패한 전제**(앞 시도가 기댄 가정과 그것이 틀렸다는
  증거)를 적는다. 같은 전제로 다시 시작하지 않게.
  - 계기 "수정이 새 결함을 들였다"는 동작이 깨졌다고 재현되는 새 `blocker`/`major` 가 수정에서 왔을 때다. `minor`, 거짓 시험, 범위 밖 변경, 규칙 위반은 계기가 아니다.
  - 이슈 안: Fix 결과에 그 Fix 를 보내던 때의 PR HEAD 에 없던 새 결함이 나왔다. 다음 Fix 는 `SendMessage` 가 아니라 한 칸 올려 새로 띄운다.
  - 이슈 사이: 이 실행에서 넣은 결함 수정(`bug` 라벨 이슈의 PR, 또는 결함을 고친 Fix 라운드가 든 PR)이 새 결함을 들였다고 밝혀졌다. 그 결함은 1단계 5항대로 이슈가 되고, 구현 등급은 원인 PR 의 구현 등급보다 한 칸 위로 매긴다(계약서 기준 등급과 견주어 높은 쪽). 원인 PR 등급이 가장 높으면 그 등급으로 보낸다(올림 없음). 모르면 계약서 기준 등급에서 한 칸. 올려 시작하면 진행 목록에 `올림 1` 로 적고, 그 뒤 이슈 안 계기나 다른 사유로 더 올리지 않는다. 올림이 없었으면(원인 PR 등급이 가장 높다) `올림 0` 이다. 새 이슈 본문에 원인 이슈와 PR 을 적는다.
  - 판정은 짐작이 아니라 재현이다. `temp-tree.sh` 사본 둘에서 수정 전 사본에서 재현이 없고 수정 사본에서 있다(이슈 안이면 수정 전은 Fix 를 보내던 때의 PR HEAD). 판정을 못 하면 계기로 치지 않는다.
  - 올림은 이슈당 한 번이다(`올림` 으로 센다). 이미 `올림 1` 이거나 가장 높은 등급이면 더 올리지 않고 `Regression warning` 만 싣고, 걸림 문단 뒤의 판단 문단에서 재리뷰, 기계 확인, 다음 PR 첫 할 일 가운데 고르며, 그것으로 풀리지 않는다고 판단할 때만 사람에게 넘긴다. 리뷰 등급은 그대로다.
  - implement-brief 의 `Regression warning` 칸(이어 하기 줄과 항상 칸)에 원인 이슈, PR, 커밋, 깨진 동작, 재현, 놓친 이유를 적는다. 계기로 올리면 `Failed premise` 대신 이것을 채운다(둘 다 해당하면 둘 다). 올리지 않고 `SendMessage` 로 보내는 Fix 에는 같은 내용을 메시지에 넣는다.
- **사람에게 넘긴다**: 올려 보낸 뒤에도 같은 이유로 막혔거나 이미 가장 높은 등급이다. `ready-for-human` 으로 옮기고
  해 본 것과 막힌 곳을 이슈 댓글로 남기고 `--release` 한다. 열린 draft PR 은 그대로 두고 보고에 적는다.

## 0. 준비

먼저 실행 위치를 본다. 접두어 없는 `/agent-dispatch` 는 낡은 사본일 수 있다.

```sh
bash "${CLAUDE_SKILL_DIR}/scripts/in-flight.sh" --where
```

마지막 줄 `VERDICT` 가 `PLUGIN` 이면 진행, `SAME`/`NONE` 이면 사본으로 돈다고 한 줄 알리고 진행한다. `STALE`,
`UNKNOWN`, 실패면 `AskUserQuestion` 으로 묻는다(멈춘다(권고) / 플러그인 이름으로 다시 부른다 / 사본으로 진행). 답이
오기 전에는 쓰기를 하지 않는다(이슈, PR, claim, worktree, 서브에이전트).

저장소 규칙(`CLAUDE.md`/`AGENTS.md`), 이슈 트래커와 triage 라벨 문서, 용어집, ADR, 사용자의 상시 선호(메모리)를 읽고
이 실행의 값을 정해 상태 블록에 적는다.

- **라벨**: `needs-triage`/`ready-for-agent`/`ready-for-human` 의 실제 문자열.
- **범위**: `지도 #<M>`, 또는 조건 하나(상태 라벨은 넣지 않는다 -- 1단계 규칙이 상태를 가른다).
- **담당**: `gh api user --jq .login`. 범위는 이 사용자의 이슈(assignee 가 없고 이 사용자가 등록했거나, 이 사용자가
  assignee)로 좁힌다. 사람이 조건에 담당을 정하면 `frontier.sh --anyone` 을 쓰고 조건에 담는다.
- **base**: 규칙이 정한 브랜치, 아니면 기본 브랜치.
- **착륙**: 규칙이 정한 착륙 명령이 하나로 묶여 있으면 그것(`land.sh --via '<명령>'`), 검사와 병합 전 단계로 나뉘어 있으면
  저장소 명령(`--check '<검사 명령>'`, `--pre-merge '<병합 전 명령>'`, push 에만 줄 env 가 있으면 `--push-env K=V`)으로 준다.
  저장소 명령이 있으면 `land.sh` 가 base 를 얹은 착륙 tip 을 만들고(아래 **병합** 이 커밋 보존이면 base 위로 rebase 하고,
  squash 면 base 를 merge 로 합친다) base 가 움직이면 다시 한다. 둘 다 없으면 gh 병합(아래 **병합**
  방식. `Base branch was modified` 로 지면 `LAND_ROUNDS` 번까지 같은 HEAD 로 다시 한다). 착륙 명령이 PR 본문을 고쳐 쓰는지, draft 를 거부하는지, 커밋 메시지에서 `Closes` 를 모으는지 읽어 둔다.
- **병합**: `rebase`, `squash`, `merge` 가운데 하나. 출처 우선순위는 실행 인자 > 저장소 규칙(`CLAUDE.md`/`AGENTS.md`) >
  사용자 상시 선호(전역 `CLAUDE.md`, 메모리) > GitHub 설정(허용된 것 가운데 rebase > squash > merge)이다. 설정은
  `gh repo view <o>/<r> --json rebaseMergeAllowed,squashMergeAllowed,mergeCommitAllowed` 로 읽는다. 정한 방식을 설정이
  허용하지 않으면 쓰기 전에 `AskUserQuestion` 으로 묻는다(조용히 바꾸지 않는다). `--via` 면 방식은 규칙이 정하고, 없으면
  rebase 로 본다. 방식은 둘로 가른다. **커밋 보존**(rebase, merge)은 커밋을 정리해 다시 쓰고 rebase 로 따라잡는다(지금까지의
  동작). **합침**(squash)은 커밋을 위에 쌓고, base 와 충돌하거나 보호 규칙이 최신을 요구하거나 `land.sh` 가 패치가 달라졌다고
  알릴 때만 `git merge origin/<base>` 로 따라잡고 force-push 하지 않는다. 이 값 하나를 구현 지시문(6단계), 리뷰 지시문과
  재리뷰(7단계), `pr-check.sh --closes-body` (7단계 1항), `land.sh --method`(8단계)가 읽는다.
- **모양 규칙**: 규칙이 막는 커밋 trailer, 브랜치에서 고치면 안 되는 경로(버전, CHANGELOG 등)를 `pr-check.sh` 의
  `--forbid-trailer`/`--forbid-path` 로 옮긴다. **판정 무관 경로**(어떤 시험도 읽지 않는 경로: version 파일, CHANGELOG
  등)를 ERE 목록으로 정한다. 7단계 "걸림"의 재리뷰 예외 (ii) 가 `--may-touch` 로 쓴다. 시험이 읽는 문서(SKILL.md 를 읽는
  정적 검사, 모든 파일을 읽는 문자 검사 등)는 넣지 않는다.
- **사본 준비**: 시험을 돌리려면 사본에 걸어야 하는 설치물(`node_modules`, `.venv` 등)을 `temp-tree.sh --link` 목록으로,
  저장소 밖에서 가져와야 하는 것을 `--copy` 로 정한다.
- **원칙**: 서브에이전트에게 넘길 상시 선호(기각한 안을 다시 권하지 않는다, 땜질보다 구조 등).

## 1. frontier 를 고르고 나눈다

```sh
bash "${CLAUDE_SKILL_DIR}/scripts/frontier.sh" --repo <owner>/<repo> (--map <M> | --query '<조건>') [--me <login>]
```

`READY` 가운데 `needs-triage` 인 것과, `ready-for-agent` 인데 열린 PR 이 없는 것이 이번 frontier 다. 진행 목록에 있는
이슈와 사람이 범위에서 뺀 이슈는 뺀다. `OTHERS` 는 넣지 않고, 지도 실행이면 마지막 보고에 `담당 밖(...)` 으로 적는다.

`BLOCKED` 는 열린 blocked_by 링크, 또는 본문 맨 앞(첫 비어 있지 않은 5줄)의 `선행: #N` 줄이 가리키는 열린 이슈 때문이다. 본문 선행이면 5열에 `선행 #K(본문)` 이 오고, 링크가 하나도 없으면 `, 링크 없음` 이 붙는다. 그 이슈는 보고의 막힘에 `선행 #K(본문)` 으로 적는다(링크를 자동으로 걸지 않는다).

**누가 쥐었는지 본다**: `bash "${CLAUDE_SKILL_DIR}/scripts/in-flight.sh" --repo <owner>/<repo> <N>...`

| 판정 | 처리 |
|---|---|
| BUSY | 다른 세션이 일한다. 건드리지 않고 보고에 적는다 |
| MAYBE | 근거 줄의 세션에 `SendMessage` 로 묻는다("#N 을 진행 중인가요? 어디까지 했는지 한 줄로"). 답이 올 때까지 빼 둔다 |
| HELD | 남은 worktree, 브랜치에 `origin/<base>` 에 없는 쓸 만한 커밋이 있으면 계약서에 넣고(바로 계약), 없으면 FREE |
| FREE | 갈래를 나눈다 |

근거 줄의 worktree, PR 이 진행 목록에 적힌 것이면 이 실행 자신이니 FREE 로 읽는다.

| 갈래 | 기준 | 처리 |
|---|---|---|
| grilling | 결정이 남았거나 본문이 코드와 어긋났을 수 있다 | 2단계 |
| 바로 계약 | 남은 일이 다 정해졌다 | 5단계 |
| 바로 구현 | `ready-for-agent` 이고 계약서의 사실 절이 지금 base 와 맞다(SHA 만 고친다) | 6단계 |
| 사람 몫 | 사내망, 실기기, 계정, 사람의 판단이 있어야 끝난다 | `ready-for-human`, 구현하지 않는다 |

맡는 이슈는 **진행 목록**에 넣고 `in-flight.sh --claim` 한다. 진행 목록은 이 실행이 손대는 이슈마다 단계(`grilling`,
`사람 답`, `구현 대기`, `구현`, `검수`, `수정`, `따라잡기`, `다음 PR 대기`, `사람 병합 대기`), agent id, worktree, PR 을
적는다. `되돌림` 과 `리뷰 라운드` 는 정보용으로 센다. `리뷰 라운드` 는 검수에서 네가 띄운 리뷰어의 수(사람이 요청한 Fix 는 세지 않는다)다. 닫히거나 사람에게 넘기거나 범위에서 빼면 진행 목록에서 빼고 `--release` 한다.

**기다림에는 깨울 사건이 있어야 한다**: 이슈 X 가 열린 이슈 K 를 기다리면, K 가 진행 목록에 있을 때만 X 의 줄에 "#K 를
기다림"을 적고 남긴다. K 가 진행 목록 밖(사람 몫, 범위 밖, 남의 세션)이면 X 를 빼고 `--release` 하고 보고에
`blocked_by #K`(본문 선행이면 `선행 #K(본문)`)로 적는다. 그래야 끝낼 조건이 참이 될 수 있다. 서브에이전트의 백그라운드
대기를 기다릴 때 깨울 사건은 그 agent 의 감시(`in-flight.sh --agent --wait`, "서브에이전트의 알림과 감시")다.

### 실행 중에 낸 이슈를 넣는다

이슈를 내는 것은 언제나 너다(서브에이전트는 내지 않는다). 대상: 어느 계약서에도 들지 않는 결함으로 재현(명령과 출력)이
있는 것 -- 네 검수, base 에서도 실패하는 시험, 서브에이전트 리포트의 계약 밖 결함(등급 무관), 이미 병합된 PR 에서 찾은
것 -- 그리고 아래의 도구 이슈. 그 PR 자체의 `minor` 와 경계 메모는 이슈로 내지 않고 착륙 기록에 남긴다.

낸 직후 차례로 한다.
1. 같은 결함의 열린 이슈가 있는지 찾는다(남이 먼저 냈으면 그 이슈에 증거를 댓글로 더하고 새로 내지 않는다).
2. `gh issue create` -- 라벨 `needs-triage`(조건 실행이면 조건의 라벨도, 결함이면 저장소에 있을 때 `bug` 라벨도), 본문에
   원인, 재현, 할 일, 완료 기준.
   저장소의 이슈 규칙(예: 사내/사외 분리)을 따른다.
3. 범위를 판정한다. 지도 실행: 지도의 코드에 있거나 지도의 PR 을 막으면 sub-issue 로 건다. 조건 실행: 조건을 이슈
   속성에 대어 판정한다(검색 색인은 늦다).
4. blocked_by 를 실제 방향대로 건다. 정수 id 를 `-F` 로 보낸다:
   `gh api repos/<o>/<r>/issues/<n> --jq .id`,
   `gh api -X POST repos/<o>/<r>/issues/<map>/sub_issues -F sub_issue_id=<id>`,
   `gh api -X POST repos/<o>/<r>/issues/<막힌 이슈>/dependencies/blocked_by -F issue_id=<막는 이슈의 id>`.
5. 새로 낸 이슈를 어떻게 진행할지 가른다.
   - 5a 버그의 뜻: 이 실행에서 네가 새로 낸 재현 있는 결함이다. 도구를 만들거나 넓히는 이슈가 도구 이슈이고, 기존 도구의
     재현 있는 결함은 버그다. 개선과 1항의 댓글만 단 이슈는 아니다.
   - 5b **즉시 진행 가능한 버그**는 넷 다 참일 때다: 이 실행의 같은 저장소 이슈이고, 사람 몫이 아니고(사내 표식 이슈
     포함), 진행 목록 밖의 열린 이슈에 막혀 있지 않고, `in-flight.sh` 가 FREE(이 실행 자신 포함)다.
   - 5c 5b 를 만족하면 범위 판정과 상관없이 진행 목록에 넣고 `--claim` 하고 바로 갈래를 나눈다(원인과 할 일이 본문에
     있으면 바로 계약). 범위 밖이면 진행 목록 줄에 `범위 밖 버그` 를 단다. 낸 버그가 이 실행에서 넣은 수정이 들인
     것이면(판정은 등급 절) `유발 #N(PR #P)` 를 달고 등급은 등급 절의 이슈 사이 계기대로 매긴다. 지도에는 3항 기준대로만 건다. 한 번에 이슈
     하나는 그대로다.
   - 5d 그 밖의 이슈는 범위 안이고 막힘이 없고 사람 몫이 아닐 때만 갈래를 나누고, 아니면 보고의 "범위 밖으로 낸
     이슈"에 이유와 함께 적는다.
   - 5e 낸 이슈의 결함 때문에 지금 이슈의 완료 기준을 채울 수 없으면 7단계 7항대로 보정한다.

### 저장소 도구를 공용화한다

**손 절차**는 스크립트를 만들었거나, 명령 여럿을 묶어 쳤거나, env, 잠금, 임시 worktree 를 매번 세운 것이다. 인자만
다른 단일 명령은 아니다. 같은 손 절차를 두 번째 하기 직전(네 것과 서브에이전트 리포트의 "만든 도구"를 합쳐 센다)에
판단한다. 이 스킬의 스크립트가 하는 일이면 그것을 쓴다. 대상 저장소에 둘 도구면
[`references/tool-sharing.md`](references/tool-sharing.md) 대로 유사 도구를 먼저 찾아 확장을 검토하고, 도구 이슈를 내고,
같은 저장소의 다른 세션에 알린다. 지금 일은 임시판으로 계속하고, 도구 이슈로 지금 일을 막지 않는다.

## 2. grilling 서브에이전트를 보낸다

grilling 갈래의 이슈마다 읽기만 하는 서브에이전트를 백그라운드로 띄운다(한 메시지에서 함께 띄워도 된다). 지시문은
[`references/grill-brief.md`](references/grill-brief.md) 를 채운다. 설계 문서, ADR, 형제 이슈를 이름으로 짚을수록 좋다.
규율 칸에는 카드의 id 와 **언제** 칸을 넣는다. 두 모양 비교 줄은 무거움 이상일 때만 남긴다. 그동안 바로 계약 갈래의 남은 일을 확인하고, 리포트와 무관한 사람 질문을 먼저 묻는다.

## 3. 리포트를 검증하고 정하거나 묻는다

리포트는 주장이다. **결정이 기대는 주장(프레임워크 동작, 죽은 코드, 줄 번호, 옮겨 간 이름, 깨지는 시험 수)은 grep 이나
실행으로 직접 확인한다.** `[추론]` 표시가 붙은 주장부터 본다. 틀린 주장이 여럿이면 그 이슈만 한 칸 올려 다시 grilling 한다. 묶음 전체를 겹쳐 보아 같은
파일, 같은 계약을 바꾸는 이슈의 순서와 경계, 아무도 맡지 않은 일을 정한다.

열린 질문마다:
- **네가 정한다**: 기록된 결정(설계 문서, ADR, 지도의 결정, 앞선 답)이 답한다 / 코드, 도구의 사실이 강제한다 / 기록된
  원칙(저장소 규칙, 상시 선호, 용어집)을 그대로 적용한 결과다 / 되돌리기 쉽고 사용자에게 보이지 않는 구현 세부다.
- **사람에게 묻는다**: 기록된 결정을 바꾸거나 그와 어긋난다 / 사용자에게 보이는 동작, 범위, 제품 판단이 갈린다 /
  근거가 어느 쪽도 강제하지 않는 trade-off / 환경, 정책, 권한(hook, CI, 배포, 계정) / 예전에 기각된 안이 되살아난다.

정한 것은 근거를 한 줄로 남긴다.

## 4. 한 라운드로 묻는다

물을 것을 이슈와 상관없이 한 번에 모아 `AskUserQuestion` 으로 묻는다. 권고를 첫 선택지로 두고 단점과 근거가 답하지
못하는 이유, 실험(읽기 전용 실행)으로도 못 가르는 이유를 함께 적는다. 질문이 걸린 이슈는 `사람 답` 이고, 나머지는 계속 진행한다. 다음 실행에서도 지킬 답은
메모리에 남긴다.

## 5. 이슈를 계약서로 다시 쓴다

본문이 구현 서브에이전트의 **계약서**다(댓글은 놓친다). 고치기 직전에 `in-flight.sh` 를 다시 돌려, 다른 세션이 집었으면
본문을 고치지 말고 그 세션에 메시지로 보낸다. 본문에 담는 것:

- **선행, 상위**: 막는 이슈, 지도, 설계 문서, ADR, 경계를 맞대는 이슈. 원 본문 맨 앞의 `선행:` 줄은 지우지 않고 유지한다(가능하면 blocked_by 링크도 건다).
- **사실(`<base> <sha>` 기준)**: 바로잡은 경로, 줄 번호, 이름. SHA 가 있어야 어긋남을 알아본다.
- **할 일**: 단계로. 사람이 정한 것은 "사용자 결정(날짜)".
- **시험**: 결함은 수정 전 빨강, 수정 후 초록. 구조 변경은 회귀를 무엇이 지키는지. 오래 걸리는 시험마다 **이어 받기
  허용 경로**(ERE, 7단계 3항 (c))를 적을 수 있다. diff 를 보기 **전에**, 여기서 정한다. 시험이 읽는 집합을 열거하지 말고
  diff 가 건드려도 결과가 바뀌지 않는 경로를 적는다(과소 선언이 거짓 승인이 되지 않게). 적지 않으면 tree 가 같을 때만
  이어 받는다. 시험 항목 끝에 `커밋별 싼 검사: <명령> 또는 없음` 을 적는다(초 단위 검사만: import, 컴파일, 수집, lint). 안 적으면 계약서는 없음이다(저장소 규칙이 정한 싼 검사는 그대로 따른다).
- **PR**: 개수(여럿이면 stacked), draft, `Closes #N` 의 자리, 버전, CHANGELOG, 본문 규칙. `Closes #N` 은 0단계 `병합` 이
  커밋 보존이거나 `착륙` 이 `--via` 면 **마지막 PR 의 마지막 커밋 메시지에도**(착륙 명령이 본문을 고쳐 써도 닫히게), 합침(squash)이고
  `--via` 가 아니면 **마지막 PR 의 본문에** 둔다. 합침이면 PR 제목이 base 에 남는 커밋 제목이니 저장소 커밋 규칙을 따른다.
- **`규율:`**: 카드 id 마다 그 이슈에서의 뜻 한 줄. 등급 상한은 가벼움 0장 / 보통 1장 이하 / 무거움 이상 3장
  이하다. 카드는 근거이지 결정이 아니다(3단계 분류를 바꾸지 않는다).
- **완료 기준**: 하나씩 확인할 수 있는 것. **범위 밖**과 **경계**.

라벨을 `ready-for-agent`(사람 몫은 `ready-for-human`)로 옮기고 단계를 `구현 대기` 로 바꾼다. 경계는 기대는 쪽 이슈에
옮기고, 지도 실행이면 지도의 결정 표를 고친다(지도와 무관한 범위 밖 버그는 빼고).

## 6. 구현 서브에이전트를 보낸다

대상은 `구현 대기` 이슈다(기본은 하나씩 -- "실행 전반의 원칙"). 보내기 직전에 `in-flight.sh` 를 다시 돌린다. 지시문은
[`references/implement-brief.md`](references/implement-brief.md) 를 채운다: `bug` 라벨이면 `diagnosing-bugs`, 그 밖은
`tdd`. 등급은 계약서를 보고 다시 매긴다(원인이 밝혀지지 않은 결함은 무거움 이상). worktree 와 브랜치 이름에 이슈 번호를
넣는다. 계약서의 `규율:` 줄에 적힌 카드는 그 본문(언제, 규칙)을 지시문의 규율 칸에 그대로 옮긴다(구현자는 카드 파일을
모른다).

**scratch**: 이슈마다 scratch 디렉터리 `<세션 scratchpad>/<N>` 를 정해 지시문의 `<scratch>` 로 넘기고 진행 목록 그 줄에
`scratch <경로>` 로 적는다. 로그, 임시 스크립트, 사본은 그 안에 남는다. 감시의 `--path` 에는 그 이슈의 worktree 와 이
scratch 를 준다("서브에이전트의 알림과 감시"). 이어 하기로 새로 띄울 때도 같은 scratch 를 넘긴다.

**이어 하기**: 이미 PR, worktree 가 있는 이슈는 그 서브에이전트에게 `SendMessage` 로 후속 요청(Fix, 따라잡기, Next PR)을
보낸다. 새로 띄우는 것은 원래 서브에이전트가 없거나 등급을 올려야 할 때뿐이고, 그때 지시문의 이어 하기 줄을 채워 두 번째
worktree, PR 이 생기지 않게 한다.

리포트가 오면: 계약서의 빈틈으로 멈췄으면 3, 4단계로 메워 계약서를 고치고 다시 보낸다. 계약 밖 결함은 1단계대로 낸다.
"만든 도구"는 공용화 판단에 센다.

## 7. 검수한다

단계는 `검수` 다. 확인은 PR HEAD 그대로 한다. 다른 커밋을 돌릴 때는 `temp-tree.sh add` 로 사본을 만들고 끝나면
`remove` 한다. 서브에이전트의 worktree 는 HEAD 와 작업 트리를 그대로 둔다.

1. **모양**:
   ```sh
   bash "${CLAUDE_SKILL_DIR}/scripts/pr-check.sh" --repo <o>/<r> --pr <P> --worktree <wt> --sha <보고한 SHA> \
     --closes <N> [--closes-body] --draft [--base <앞 층 브랜치>] [--forbid-trailer '<ERE>']... [--forbid-path '<ERE>']... \
     [--verdict '<로그>=<글자>']... [--carry <sha> [--may-touch '<ERE>']...]...
   ```
   `--closes-body` 는 0단계 `병합` 이 squash 이고 `착륙` 이 `--via` 가 아닐 때 준다(`Closes #N` 을 PR 본문에서 찾는다).
   `SHAPE FAIL` 이면 리뷰어를 띄우지 않고 그것부터 Fix/따라잡기로 돌려보낸다. stacked PR 의 아래층은 `--closes` 를 빼고
   위층은 `--base <앞 층 브랜치>` 를 준다. 검수 중인 PR 은 늘 draft 다(`--draft`). 8단계의 `land.sh` 가 ready 로 바꾼 뒤
   `BLOCKED` 로 돌아온 PR 이면 `gh pr ready --undo` 로 되돌리고 돈다.
2. **리뷰어를 띄운다**(`SHAPE OK` 직후, 이 PR 에 아직 리뷰가 없을 때): [`references/review-brief.md`](references/review-brief.md)
   를 채워 백그라운드로. 스택이면 스택 전체를 한 리뷰로 본다. 진행 목록에 `리뷰한 SHA` 와 리뷰어 id 를 적는다. Fix,
   따라잡기 뒤의 재리뷰는 아래 "걸림" 문단대로 한다.
3. **시험을 다시 돌린다**(리뷰어와 나란히): 계약서의 시험마다 PR HEAD 의 증거가 다음 셋 가운데 하나여야 한다. 셋 다
   아니면 다시 돌린다. 리포트의 숫자를 옮겨 적지 않는다.
   - (a) **재실행**: 너나 네가 띄운 서브에이전트가 PR HEAD 에서 다시 돌린 결과.
     구현자의 좁힌 실행은 증거가 아니다.
     오래 걸리는 것은 서브에이전트(`haiku`/`max`)에 맡기되
     로그 파일을 worktree 밖에 남기게 하고 판정 줄을 네가 직접 읽는다. 하위 에이전트의 "통과" 요약만으로 받지 않는다.
     그 지시에는 기다림 규칙을 넣는다(implement-brief 의 `**Waiting**` 줄을 그대로 옮긴다): 긴 실행은 그 실행 자체를
     `run_in_background` 로 띄우고 `&`, `nohup`, `setsid`, `( ... & )` 로 떼어 띄우지 않는다. 로그나 다른 task 출력을
     폴링하는 루프를 쓰지 않는다(꼭 써야 하면 `timeout` 으로 묶고 기다리는 실행이 끝나면 루프도 끝나게 한다). 마지막이
     아닌 턴을 끝내며 기다릴 때는 무엇을 기다리고 언제 끝날지 그 실행의 로그 경로와 함께 한 줄로 쓴다. 리포트 전에는 띄운
     백그라운드 실행이 끝나기를 기다리거나 `TaskStop` 하고, 멈춘 것을 리포트에 적어 아무것도 남기지 않는다.
   - (b) **판정 줄**: 실행기가 실행 시점에 **스스로 계산해** 찍은 40자 SHA 가 든 판정 줄. SHA 가 PR `headRefOid` 와 같고,
     줄에 계약서의 시험 id 가 들어 있고, 로그가 worktree 밖에 있어야 한다(8단계 뒷정리가 worktree 를 지운다). 에이전트가
     인자로 넘긴 SHA 를 그대로 찍는 실행기는 안 된다. 실행기 코드에서 SHA 를 계산하는 `file:line` 을 확인한다. 판정은
     1항에 `--verdict '<로그>=<판정 줄, SHA 자리는 {sha}>'` 를 더해 한다. 판정 줄 글자는 앞뒤 구분자까지 넣어 실패 줄에
     맞지 않게 고유하게 쓴다(`--verdict` 는 줄의 어디서든 고정 문자열로 찾는다. 예: `통과: {sha}` 는 `불통과: <sha>` 에도
     맞는다).
   - (c) **이어 받기**: 앞 SHA 의 결과를 받는다. 그 SHA 는 결과가 실제로 생산된 SHA 여야 한다(이어 받은 결과를 다시
     이어 받지 않는다). 1항에 `--carry <그 SHA> [--may-touch '<계약서가 그 시험에 적은 이어 받기 허용 경로>']...` 를 더해
     tree diff(`git diff --no-renames --name-only <sha> HEAD`, rename 은 옛 경로와 새 경로 둘 다)로 본다. base 가
     움직였으면 형제 PR 의 변경도 그 시험의 입력이라 diff 에 든다. tree 가 같으면 받고, 다르면 diff 가 허용 경로에만 맞을
     때 받는다. 선언이 없으면 tree 가 같을 때만.

   `EVIDENCE OK` 는 받고 `RERUN` 은 다시 돌린다. 라벨은 `verdict#<k> <로그>` 나 `carry#<k> <SHA 12자>` 이고 k 는 그
   옵션을 준 순번이다. 이 줄들은 `SHAPE` 와 exit 를 바꾸지 않는다(증거 부족은 PR 결함이 아니라
   "다시 돌려라"다). PR 이 건드리지 않은 기존 시험이 실패하면 `origin/<base>` 사본에서 같은
   시험을 돌려, 같은 자리에서 같은 메시지로 지면 이 PR 의 걸림이 아니다(1단계대로 이슈를 낸다). PR 이 더하거나 바꾼
   시험, 계약서가 정한 시험의 실패는 언제나 걸림이다.
4. **계약 대조**: 할 일이 다 들어갔는가, 범위 밖 변경이 없는가, 막힌 파일을 건드리지 않았는가, 바뀐 기존 단언마다 이유가
   있는가. 구현자의 규율 보고가 계약서의 `규율:` 줄과 맞는가(보고한 바꾼 선택이 diff 의 그 자리에 있는가). 규율 보고는
   리뷰어에게 주지 않는다(리뷰어는 계약서와 코드만 본다).
5. **주장을 재현한다**: 결과를 좌우하는 주장 하나 이상을 사본에서 직접 재현한다. "수정 전에는 빨강" -> 수정 전 커밋
   사본에서 그 시험을 돌린다. "이 시험이 이 결정을 지킨다" -> `mutate.sh` 로 그 결정을 깨 KILLED 인지 본다.
   재현과 변이는 그 주장에 닿는 시험만 돌려도 된다.
6. **리뷰 결과를 판정한다**: 근거가 선 행은 받고 없는 행은 사유와 함께 기각한다. 계약 안의 `blocker`/`major` 는 Fix 에,
   `minor` 는 착륙 기록의 후속 메모로. 계약 밖으로 재현이 있는 것은 1단계대로 이슈를 내고 Fix 에 넣지 않는다. 단 이 PR 의 Fix 가 들인 회귀는 계약 밖 영역이라도 이 PR 의 Fix 에 넣는다(판정은 등급 절).
7. **계약과 다른 점**: 받아들인 것은 계약서에 반영한다. 범위 밖 회귀 때문에 완료 기준 하나를 채울 수 없으면 그 회귀를
   이슈로 내고, 기준을 어떻게 보는지(예: "base 와 견주어 새 실패가 없으면 충족")를 이슈 댓글로 남긴다.

**깨끗하다**는 다음이 모두 참일 때다: `SHAPE OK` / 계약서의 시험이 PR HEAD 에서 초록(시험마다 3항의 증거 (a), (b), (c)
가운데 하나, base 에서도 지는 것은 이슈로 냄) /
받아들인 계약 안의 `blocker`/`major` 가 없다 / 완료 기준이 채워졌다(보정한 것은 댓글이 있다) / 계약 대조와 재현이
맞다. 단 걸림 문단 뒤의 판단 문단이 **다음 PR 첫 할 일** 로 넘긴 지적은, 착륙 기록에 `판단:` 줄이 있으면 받아들인 `blocker`/`major` 로 치지 않는다. 깨끗하면 8단계로 간다.

**걸림**: 1~7의 걸린 것을 모두 모아 Fix 를 **한 번에** 보낸다(단계 `수정`). 고쳐 오면 1항부터 다시 한다. Fix 결과가 새 결함을 들였다고 판정되면(등급 절) 다음 Fix 는 한 칸 올려 다시 보낸다(등급 절의 올림 한 번 규칙대로). Fix 나 따라잡기
뒤에는 **기본이 재리뷰다**(사용자 결정 2026-11-24). 다음 닫힌 예외에 들 때만 기계 재검사(1, 3, 4항과, 리뷰가 살아남았다고
한 변이를 `mutate.sh` 로 다시)로 끝낸다. 너의 "뜻이 안 바뀌었다"는 판단은 예외가 아니다. 파일 종류로도 가르지 않는다.
시험 파일, fixture, 시험이 읽는 문서(SKILL.md 를 읽는 정적 검사 등)가 바뀐 Fix 는 모두 재리뷰한다.

- (i) `git rev-parse <리뷰한 SHA>^{tree}` 와 `HEAD^{tree}` 가 같다(메시지, 이력만 바뀜). base 가 움직였으면 range-diff 가
  비어 있다.
- (ii) `리뷰한 SHA` 이후 diff 의 경로가 모두 0단계의 판정 무관 경로에 맞는다. 1항에 `--carry <리뷰한 SHA> --may-touch
  '<판정 무관 ERE>'...` 를 더해 `EVIDENCE OK carry#<k> ...` 가 나와야 한다.
- (iii) 구현자가 충돌 없이, 또는 기계적으로 풀었다고 보고한 따라잡기로, 패치가 같다. 명령은 0단계 `병합` 으로 갈린다.
  - 커밋 보존: `git log -p -U0 --reverse <mb>..<리뷰한 SHA> | git patch-id --stable` 과
    `git log -p -U0 --reverse <mb'>..HEAD | git patch-id --stable` 의 patch-id 열 목록(순서, 개수 포함)이 같다(`<mb>` 는
    `git merge-base <리뷰한 SHA> origin/<base>`, `<mb'>` 는 `git merge-base HEAD origin/<base>`). 범위에 merge 커밋이 있거나
    한쪽이 비면 예외가 아니다. `land.sh` 의 커밋 패치 판정과 같은 명령이다.
  - 합침(squash): PR 고유 diff 의 patch-id 가 같다:
    `git diff -U0 $(git merge-base <리뷰한 SHA> origin/<base>) <리뷰한 SHA> | git patch-id --stable` 과
    `git diff -U0 $(git merge-base HEAD origin/<base>) HEAD | git patch-id --stable` 의 patch-id 열이 같다. 따라잡기 merge 커밋이
    범위에 있어도 된다. 한쪽이 비면 예외가 아니다. `land.sh` 의 고유 diff 판정과 같은 명령이다.

재리뷰는 1항 `SHAPE OK` 직후(예외 (ii) 는 1항의 `--carry` 로, (i) 은 `rev-parse`, (iii) 은 patch-id 비교로 직접) 3, 4항과 **나란히** 띄운다(새
직렬 단계가 아니다). 대상은 커밋 보존이면 `리뷰한 SHA` 이후의 diff 다(base 가 움직였으면 `git range-diff`). 합침(squash)이면
`git diff <리뷰한 SHA>..HEAD` 가 아니라(따라잡기 merge 뒤에는 형제 PR 의 파일까지 끌어온다) PR 고유 diff 둘
(`git diff $(git merge-base <리뷰한 SHA> origin/<base>) <리뷰한 SHA>` 와 `git diff $(git merge-base HEAD origin/<base>) HEAD`)의
비교다(review-brief 의 재리뷰 줄). 크기는 첫 리뷰 열보다 한 칸
아래, 하한 `sonnet`/`high`. 가벼움 PR 은 처음부터 리뷰가 없으니 재리뷰도 없다.

리뷰를 거듭해도 같은 지적이 남거나 새 지적이 이어지면, 남은 지적의 크기와 성격을 보고 다음 중 하나를 네가 고른다. 숫자 상한은 두지 않는다.

- 재리뷰 한 번 더.
- **기계 확인**: 남은 지적이 모두 판정 술어(이름 붙은 시험의 빨강->초록, `mutate.sh` 의 SURVIVED->KILLED, 고정 문자열 grep)로
  가를 수 있고, 그 술어를 Fix 를 보내기 **전에** 정해 둘 수 있을 때. 이 처리는 위의 닫힌 예외 (i)~(iii) 규칙보다 앞선다. Fix 뒤 그 술어와 1, 3, 4항으로 끝내고, Fix diff 가 지적의 경로에만 닿는지
  `pr-check.sh --carry <리뷰한 SHA> --may-touch '<지적 경로>'` 로 본다.
- **다음 PR 첫 할 일**: 같은 이슈에 다음 PR 이 있고 남은 지적이 완료 기준을 깨지 않을 때. 계약서의 그 PR 할 일 맨 앞에 재현,
  기대, 출처 PR 과 SHA 를 적는다. 한 번 넘긴 지적은 다시 넘기지 않는다.
- 한 칸 올림(등급 절, 올림을 아직 쓰지 않았을 때).
- 사람에게 넘긴다(위 처리로 풀리지 않는다고 판단했을 때).

고른 처리로 풀리지 않은 지적에는 같은 처리를 다시 고르지 않는다.

착륙한다면 착륙 기록에 `판단:` 한 줄(고른 처리, 남은 지적, 근거 재현)과 `리뷰하지 못한 범위` 를 남긴다.

## 8. 넣는다

1. **착륙 기록**을 파일로 쓴다: 시험마다 증거 종류(7단계 3항의 a/b/c)와 근거 -- (a) 명령과 결과, (b) 로그 경로와
   **판정 줄 원문 인용**, 실행기에서 SHA 를 계산하는 `file:line`, (c) 이어 받은 SHA 와 `EVIDENCE OK` 줄(diff --stat).
   그리고 재현한 주장, 계기가 있었으면 계기(이슈 안 / 이슈 사이)와 올린 등급, 리뷰 요지(받은 것, 기각한 것과 사유), `minor` 후속 메모, 계약과 다른 점, 리뷰하지 못한 범위, 걸림 문단 뒤의 판단 문단에서 고른 처리가 있었으면 `판단:` 한 줄. PR 본문이 착륙 명령에 고쳐 써져도 이슈에 남는다.
   계약서에 `규율:` 줄이 있었으면 규율 한 줄(어느 카드가 어떤 선택을 바꿨나)도 싣는다.
2. 넣는다. 스택이면 마지막 층만 넣는다.
   ```sh
   bash "${CLAUDE_SKILL_DIR}/scripts/land.sh" --repo <o>/<r> --pr <P> --sha <검수한 PR HEAD> --issue <N> \
     --evidence <기록 파일> (--method <0단계 병합> | --via '<착륙 명령>') [--base <base> --close-stack <앞 층 PR,...>] [--keep] \
     [--check '<검사 명령>'] [--pre-merge '<병합 전 명령>'] [--push-env K=V]...
   ```
   `--via` 와 저장소 명령(`--check`, `--pre-merge`, `--push-env`)은 함께 주지 않는다. 0단계 `착륙` 에 적은 쪽을 준다.
   `--method` 는 언제나 0단계 `병합` 값을 준다(`land.sh` 의 기본인 설정 순서에 맡기지 않는다). `--via` 면 빼고 착륙 명령이 넣는다.
   `<검수한 PR HEAD>` 는 7단계를 마지막으로 1항부터 돌았을 때 확인한 PR HEAD 다(리뷰가 없었던 가벼움 PR, 예외로 끝낸 Fix
   포함). 진행 목록의 `검수한 SHA` 다.
   `--keep` 은 계약서에 다음 PR 이 남았을 때다. 권한 설정이 이 명령을 막으면 사람에게 허용 규칙(예:
   `Bash(bash *agent-dispatch/scripts/land.sh*)`)을 더해 달라고 하고 기다린다.
3. 마지막 줄로 가른다.

| 결과 | 처리 |
|---|---|
| `LANDED #P <sha> ISSUE #N CLOSED` | 진행 목록에서 빼고 `--release`. 줄에 `범위 밖 버그` 표식이 있었으면 `처리한 착륙` 에 `#<PR>(#<이슈>, 범위 밖 버그)` 로 옮긴다. `유발` 표식이 있었으면 `유발 #<n>` 도 함께 옮긴다. 1단계로(이 병합으로 풀린 이슈가 들어온다) |
| `LANDED ... ISSUE #N OPEN` | 계약서에 다음 PR 이 남았으면 단계 `다음 PR 대기`, Next PR 요청. 남은 PR 이 없으면 완료 기준을 확인해 닫거나 이유를 적는다 |
| `BLOCKED ... PR HEAD 가 검수한 SHA 와 다르다` | 검수 뒤 누가 push 했다. 7단계 1항부터 새 HEAD 로. 단 그 HEAD 가 앞 `land.sh` 실행의 stderr 에 `land: 올린 tip <그 HEAD 40자>` 로 나온 것이면(복원 실패, kill 로 죽은 실행) 그 실행의 `--push-env` 를 함께 주어 `env K=V... git push --force-with-lease=refs/heads/<branch>:<그 HEAD> <remote> <검수한 SHA>:refs/heads/<branch>` 로 되돌리고 같은 `--sha` 로 다시 부른다 |
| `BLOCKED ... PR 이 열려 있지 않다(MERGED)` | 병합 뒤 정리 전에 끝났다. `land.sh --cleanup --repo <o>/<r> --pr <P> --issue <N>` 으로 뒷정리하고 `LANDED` 처리를 한다. `(CLOSED)` 면 누가 닫았으니 사람에게 넘긴다 |
| `BLOCKED ... 저장소가 <방식> 병합을 허용하지 않는다` | `--method` 로 준 방식을 저장소 설정이 막았다. 기록, 대상 변경, push, ready 전에 멈췄으니 PR 은 draft 그대로다. 0단계 `병합` 방식을 고치거나(규칙과 설정을 다시 읽는다) `AskUserQuestion` 으로 사람에게 묻고, 정한 방식으로 다시 부른다 |
| `BLOCKED ... base 와 충돌한다 -- 따라잡기가 필요하다` | 따라잡기 요청(단계 `따라잡기`). 충돌 파일은 stderr 에 있다. 돌아오면 7단계 |
| `BLOCKED ... base 를 합치지 못했다: <오류>` | 고리 모드(커밋 보존, squash 모두)에서 충돌 파일 없이 base 를 얹는 rebase 나 merge 가 졌다(PR 탓이 아니다). 오류 줄과 stderr 를 읽고 저장소 설정, 훅, 디스크처럼 환경 탓이면 고쳐 같은 명령으로 다시 부르고, 네가 풀 수 없으면 사람에게 넘긴다 |
| `BLOCKED ... base 를 얹은 뒤 패치가 달라졌다` | 따라잡기 요청(단계 `따라잡기`). 0단계 `병합` 이 squash 면 요청에 이 판정 줄을 적는다(구현자는 그때 `git merge origin/<base>` 로 따라잡는다). 돌아오면 7단계(재리뷰가 기본) |
| `BLOCKED ... 검사 실패: <cmd>` | stderr 의 출력을 읽고 Fix(단계 `수정`). PR 은 draft 로 남아 있다 |
| `BLOCKED ... 병합 전 명령이 실패했다: <cmd>` | stderr 의 출력을 읽는다. 저장소 쪽 일시 오류면 한 번 더, PR 탓이면 Fix(단계 `수정`) |
| `BLOCKED ... base 가 움직여 <N>번 다시 했다` | 저장소 명령으로 넣을 때도, gh 로 넣을 때도 나온다. 한 번 더 부른다. 또 그러면 사람에게 넘긴다 |
| `BLOCKED ... PR HEAD 가 병합 직전에 바뀌었다` | 검수 뒤 HEAD 가 바뀌었다(사람 승인이 아니다). 7단계 1항부터 새 HEAD 로 검수한다. 저장소 명령으로 넣었는데 stderr 에 `되돌리지 못했다` 가 있으면, 남이 올린 HEAD 를 덮지 않은 것이다 |
| `BLOCKED ... PR 브랜치에 push 하지 못했다` | PR HEAD 를 본다. 검수한 SHA 도, stderr 의 `land: 올린 tip` 도 아니면 lease 가 막은 것(검수 뒤 남이 push 했다)이니 `검수한 SHA 와 다르다` 와 같이 한다. 그대로면 원격 오류이니 한 번 더 부르고, 또 그러면 stderr 를 읽고 처리한다 |
| `BLOCKED ... PR HEAD 가 올린 tip <sha> 이 되지 않았다` | GitHub 반영이 늦었거나 남이 push 했다. 한 번 더 부르고, `검수한 SHA 와 다르다` 가 나오면 그 행대로 한다 |
| `BLOCKED ... PR 을 읽지 못했다`, `검증 기록을 #<N> 에 남기지 못했다`, `대상 브랜치를 <b> 로 바꾸지 못했다`, `base <b> 를 받지 못했다`, `임시 worktree 를 만들지 못했다`, `임시 디렉터리를 만들지 못했다`, `mergeable 이 끝내 UNKNOWN 이다`, `ready 로 바꾸지 못했다`, `저장소의 병합 방식을 읽지 못했다`, `gh pr merge 실패: <오류>` | 일시 오류이거나 GitHub 반영이 늦을 수 있다. PR 브랜치는 검수한 SHA 다(저장소 명령으로 넣었으면 `land.sh` 가 올린 tip 을 되돌렸다. 되돌리지 못했으면 stderr 에 그렇게 나오고 다음 실행이 `검수한 SHA 와 다르다` 로 멈춘다). 같은 명령으로 한 번 더 부르고, 또 그러면 stderr 와 오류 줄을 읽는다: PR 탓이면 Fix(단계 `수정`)나 따라잡기, 네트워크, 디스크, 권한, 저장소 설정처럼 네가 풀 수 없으면 사람에게 넘긴다 |
| `BLOCKED ... gh pr merge 뒤에도 <state> 다`, `착륙 명령은 끝났는데 PR 이 <state> 다` | 병합 호출(착륙 명령)은 끝났는데 아직 MERGED 가 아니다(병합 큐, 반영 지연). `land.sh` 를 같은 `--sha` 로 다시 부르거나 PR 브랜치를 되돌리지 않는다(저장소 명령으로 넣어 push 했으면, 곧 stderr 에 `land: 올린 tip` 줄이 있으면 PR HEAD 는 그 tip 이고, 그 줄이 없으면 검수한 SHA 그대로다). 착륙 명령이면 그 출력을 읽는다. `NEEDS_HUMAN` 처럼 9단계로 지켜보고, MERGED 가 되면 `land.sh --cleanup --repo <o>/<r> --pr <P> --issue <N>`, 닫히거나 큐에서 빠지면 사람에게 넘긴다 |
| `BLOCKED ... --via 를 돌릴 <branch> 의 worktree 가 없다` | PR 브랜치를 체크아웃한 worktree 가 없다. `git worktree add <경로> <branch>` 로 만들고 같은 명령으로 다시 부른다 |
| `BLOCKED ... 병합되지 않았다(<state>) -- 정리하지 않는다` | `--cleanup` 을 병합 전에 불렀다. 9단계 지켜보기를 이어 가 MERGED 가 된 뒤 다시 부른다 |
| `BLOCKED ... 착륙 명령이 실패했다` | 그 출력을 읽는다. 저장소 검사 실패면 Fix, 충돌이면 따라잡기, base 가 움직여 다시 하면 되는 것이면 한 번 더 |
| `NEEDS_HUMAN #P ...` | 보호 규칙이 사람의 승인을 요구한다. 단계 `사람 병합 대기`, 9단계로 지켜본다. 저장소 명령으로 넣어 push 했으면(stderr 에 `land: 올린 tip` 줄이 있으면) PR HEAD 는 검수한 SHA 가 아니라 그 tip(사람이 넣을 착륙 tip 과 병합 전 커밋)으로 남는다. 그때는 옛 `--sha` 로 `land.sh` 를 다시 부르지 않는다(`검수한 SHA 와 다르다` 로 멈추고, 그 행의 손 복원이 사람이 넣을 판을 지운다). 그 줄이 없으면(base 가 이미 조상이고 병합 전 커밋이 없었으면) 올린 것이 없어 PR HEAD 는 검수한 SHA 그대로다. 사람이 넣으면 `land.sh --cleanup --repo <o>/<r> --pr <P> --issue <N>` 으로 뒷정리한다 |

넣은 뒤 진행 중인 다른 PR(병렬로 돌린 경우)이 같은 파일, 계약에 닿으면 사본에서 새 base 위로 올려 시험을 다시 돌리고,
깨지면 Fix 로 돌려보낸다.

## 9. 보고하고 이어 가거나 끝낸다

이슈를 넣을 때마다, 그리고 사람이 알아야 할 일이 생길 때마다 짧게 보고한다: 이슈마다 상태 한 줄(갈래, PR, 등급과 신호),
검수 결과(다시 돌린 시험, 재현한 주장, 되돌린 것과 결말, 판단이 든 기각), 네가 정한 것 가운데 판단이 든 것, 실행 중에
낸 이슈와 처리, 공용화 후보와 처리, 진행 중이라 건너뛴 이슈와 그 세션, 주인 없이 남은 worktree.

**범위 안에서 열려 있는 이슈**는 보고에 진행 목록의 단계, 이름 붙은 막힘(`blocked_by #N` 또는 `선행 #N(본문)`, `사람 답`, `ready-for-human`,
BUSY 와 세션 이름, `사람 병합 대기 PR #N`), 범위 밖 이유 가운데 하나로만 적는다. 진행 목록의 범위 밖 버그는 단계나 이름 붙은 막힘으로 적는다. "다음 차례", "나중에" 같은 이유 없는
미룸은 쓰지 않는다. 보고 직전에 `frontier.sh` 를 다시 돌려 그 꼴에 들지 않는 이슈가 있으면 1단계 갈래를 나눈다.

서브에이전트가 **일하는 중**이라고 쓰려면 그 직전에 `in-flight.sh --agent <id> --path <worktree> --path <scratch>` 를
`--wait` 없이 한 번 돌려 그 판정 줄(`WORKING ...`)을 근거로 싣는다. 커밋, 로그 mtime, PR, 살아 있는 프로세스만으로
일한다고 쓰지 않는다. `STALLED` 면 보고 전에 깨운다("서브에이전트의 알림과 감시").

**지켜보기**는 사람이 넣어야 하는 PR(`NEEDS_HUMAN`)과, 범위 안의 이슈를 막는 남의 PR 이 있을 때만 건다. 방법과 일마다의
처리는 [`references/watching.md`](references/watching.md) 에 있다.

**끝낸다**: 진행 목록이 비었고, 지켜볼 PR 이 없고, `frontier.sh` 에 고를 frontier 가 없으면 마지막 보고를 하고 멈춘다.
마지막 보고에는 닫힌 이슈와 PR, 남은 이슈와 이유(사람이 풀어야 할 것 먼저), 지도 실행의 담당 밖 이슈, 함께 처리한 범위 밖 버그, 정리한 worktree 와
주인 없이 남은 것을 싣는다. 사람이 멈추라 하면 그 자리에서 서브에이전트와 지켜보기를 멈추고 보고한다.

**상태 블록**: 맥락이 요약되면 기억할 수 있는 것은 이것뿐이다. 보고 끝에 두고, 진행 목록이 바뀔 때마다 다시 낸다.

```
위치 <VERDICT>, <답|해당 없음>
범위 <지도 #M | 질의 "q">, 담당 <me|조건>, base <b>, 착륙 <--via '<명령>' | gh[ --check '<명령>'][ --pre-merge '<명령>'][ --push-env K=V]...>, 병합 <rebase|squash|merge>, 라벨 <셋>, 모양 <forbid 목록, 판정 무관 ERE>, 사본 <link/copy 목록>, 원칙 <한 줄>
처리한 착륙: #<PR>(#<이슈>[, 범위 밖 버그][, 유발 #<n>]) ...
범위 밖으로 낸 이슈(즉시 진행 불가 버그, 버그 아닌 이슈): #<n> <이유> | 없음
공용화 후보: <손 절차> x<횟수> -> <도구 이슈 #n | 기존 도구 확장 | 일회용> | 없음
범위에서 뺀 이슈: #<x> | 없음
지켜보기: task <id> -- #<PR> ... | 없음
진행 목록:
  #<x> grilling, agent <id>, 감시 <task id|없음>[, 깨움 <epoch>]
  #<y> 사람 답, Q<k>
  #<z> 수정, agent <id>, <등급>(올림 0|1), 되돌림 <n>, 리뷰 라운드 <n>, 리뷰한 SHA <sha|없음>, 검수한 SHA <sha|없음>, 리뷰어 <id|없음>, worktree <경로>, scratch <경로>, 감시 <task id|없음>[, 깨움 <epoch>], PR #<d>[, 범위 밖 버그][, 유발 #<n>(PR #<p>)]
  #<w> 구현 대기[, #<K> 를 기다림][, 범위 밖 버그][, 유발 #<n>(PR #<p>)]
물어 둔 세션: #<n> -> <이름> | 없음
```
