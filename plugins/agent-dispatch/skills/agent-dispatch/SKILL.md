# agent-dispatch — 지도 이슈를 frontier 마다 grilling·결정·구현·검수까지, 지도가 끝날 때까지

**지도 이슈**(sub-issue 나 목록으로 하위 이슈를 묶은 큰 작업) 하나를 받아, 지금 착수할 수 있는 이슈 묶음인
**frontier** 를 전진시킨다. 너는 **오케스트레이터**다.

- 이슈마다 서브에이전트가 스스로 grilling 해서 설계 트리를 가져온다.
- 너는 묶음 전체를 보고, 근거가 답하는 것은 직접 정한다. 사람의 판단이 필요한 것만 한 라운드로 묻는다.
- 정해지면 이슈를 계약서로 다시 쓰고 `ready-for-agent` 로 옮긴다.
- 그 이슈들을 종류에 따라 구현 서브에이전트에 맡긴다. 서브에이전트는 자기 적대적 리뷰어를 띄워 찾은 것을
  반영한 뒤에 PR 을 넘긴다.
- 너는 넘어온 PR 을 직접 **최종 검수**한 뒤 사람에게 넘긴다.

frontier 는 병합이 쌓여야 전진한다. 병합은 사람 몫이므로, 너는 PR 을 지켜보다가 병합되면 정리하고 1단계로
돌아간다. 한 번 부르면 **지도가 끝날 때까지** 돈다(9단계). 사람이 다시 부르기를 기다리지 않는다.

필요한 스킬: `grilling`·`domain-modeling`·`tdd`·`diagnosing-bugs`(mattpocock-skills). 목록에 플러그인 접두어가
붙어 있으면(`mattpocock-skills:tdd`) 그 이름으로 부른다.
- 서브에이전트는 이 스킬들을 직접 부른다. `grill-with-docs` 는 `grilling` + `domain-modeling` 을 부르는 것이
  전부이고, `implement` 의 축은 `tdd` 와 리뷰다. 이 둘은 사용자 전용이라 서브에이전트가 부를 수 없다. 리뷰는
  아래의 적대적 리뷰어가 맡는다.
- `references/` 의 지시문 틀이 더하는 것은 그 스킬들에 없는 오케스트레이션 몫이다.
  - grilling 쪽: 사람 없이 스스로 grilling 하는 법과, 돌려줄 리포트의 모양.
  - 구현 쪽: 이슈 본문이 계약서라는 것, 자기 worktree 와 이어 하기, 적대적 리뷰 반영, draft PR, 후속 요청(수정·
    rebase), 멈출 조건, 보고 형식.
  - 리뷰 쪽: 계약서와 코드만 받아 변경을 깨뜨리려 드는 리뷰어의 공격 축과 증거 기준.

## 0. 저장소 규칙을 읽는다

다음을 읽고, 이 실행에서 쓸 값을 정한다.
- 저장소 `CLAUDE.md`/`AGENTS.md`: 작업 트리(worktree) 규칙, 시험·CI, PR·병합, 버전·CHANGELOG, 소유권, 이슈 규칙.
- 이슈 트래커 문서와 triage 라벨 표(mattpocock 설정이면 `docs/agents/issue-tracker.md`·`triage-labels.md`):
  `needs-triage`·`ready-for-agent`·`ready-for-human` 의 실제 라벨 문자열.
- 용어집(`CONTEXT.md`/`GLOSSARY.md`)과 ADR 폴더의 위치.
- 사용자의 상시 선호(메모리): 서브에이전트에게 넘길 원칙(예: 기각한 안을 다시 권하지 않는다, 땜질보다 구조).

완료 기준: 라벨 문자열 셋, 이슈 저장소, 서브에이전트에 붙일 원칙 목록이 정해졌다.

## 1. frontier 를 고르고 나눈다

지도의 하위 이슈 가운데 **열려 있고, 열린 blocked_by 가 없는** 것을 모은다. 그중 `needs-triage` 인 것과,
`ready-for-agent` 인데 열린 PR 이 없는 것이 이번 frontier 다. 뒤쪽은 앞선 실행에서 계약을 마치고 선행 PR 의
병합을 기다리던 이슈다. 이 실행의 **진행 목록**에 있는 이슈는 뺀다. 이 실행에서 계약한 이슈는 진행 목록에서 곧장
6단계로 간다. GitHub 이면:

```sh
gh api "repos/<owner>/<repo>/issues/<map>/sub_issues?per_page=100" \
  --jq '.[] | select(.state=="open" and .issue_dependencies_summary.blocked_by==0)
        | "#\(.number) \([.labels[].name]|join(",")) \(.title)"'
```

sub-issue 가 없는 트래커는 지도 본문의 목록과 각 이슈 맨 앞의 `Blocked by:`·`⛔ 선행` 줄로 같은 것을 고른다.
지도 본문이 "지금 착수할 수 있는 것"으로 따로 꼽은 이슈도 넣는다.

**진행 목록**은 이 실행이 지금 손대고 있는 이슈의 목록이다. 회차가 겹치면 이 목록 없이는 같은 이슈를 다시
집는다. `in-flight.sh` 가 자기 세션을 보지 않기 때문이다.
- **이슈마다 적는 것**: 단계, 서브에이전트의 agent id, worktree, PR, 상한을 세는 값(8단계 상태 블록). 단계는 다음
  가운데 하나다: `grilling` · `사람 답` · `구현 대기` · `구현` · `검수` · `수정` · `rebase` · `다음 PR 대기` ·
  `병합 대기`.
- **넣는다**: 아래 갈래에서 grilling·바로 계약·바로 구현으로 가를 때. 이때 `--claim` 한다. 첫 단계는 grilling·바로
  계약이면 `grilling`, 바로 구현이면 `구현 대기` 다.
- **뺀다**: 이슈가 닫혔을 때, 사람에게 넘겼을 때, 지도에서 뺐을 때. 이때 `--release` 한다. 그 밖에는 PR 이 없는
  구간(사람 답·다음 PR 대기)에도 남기고 claim 도 유지한다. 다른 세션이 그 틈에 집지 않게 하려는 것이다.
- **자기 것 알아보기**: `in-flight.sh` 는 이 실행의 서브에이전트가 만든 worktree 를 HELD 로, 이 실행이 연 PR 을
  BUSY 로 낸다. 근거 줄의 worktree·PR 이 진행 목록에 적힌 것이면 그 판정은 이 실행 자신이다. 5·6단계 직전
  확인에서는 FREE 로 읽는다.

### 이미 누가 쥐고 있는지 본다

같은 PC 에 떠 있는 다른 Claude Code 세션이 그 이슈를 이미 진행하고 있을 수 있다. 저장소 체크아웃 안에서 판정
스크립트를 돌린다.

```sh
bash "${CLAUDE_PLUGIN_ROOT}/skills/agent-dispatch/scripts/in-flight.sh" --repo <owner>/<repo> <N>...
```

스크립트는 다음을 근거로 이슈마다 판정 하나와 근거 줄을 낸다.
- 살아 있는 세션 파일(`~/.claude/sessions`)과 그 세션 기록의 작업 디렉터리·명령·사람 지시.
- 이슈 번호가 든 worktree·브랜치, 열린 PR.
- 다른 `agent-dispatch` 실행이 남긴 "맡았다" 표시.

| 판정 | 뜻 | 처리 |
|---|---|---|
| **BUSY** | 다른 세션이 그 이슈의 worktree 에서 일한다 / 맡았다고 표시했다 / 그 이슈의 열린 PR 이 있다 | **이미 진행 중** 갈래 |
| **MAYBE** | 다른 세션이 그 worktree 경로로 명령을 돌렸거나, 그 세션의 사람 지시에 `#N` 이 나온다, 또는 `Refs #N` 만 있는 PR | 아래 "묻기" |
| **HELD** | 이슈 번호가 든 worktree·브랜치가 남았는데, 거기서 일하는 세션이 없다 | 아래 "남은 것 보기" |
| **FREE** | 위 어느 것도 없다 | 갈래 나누기로 |

- **묻기**: 근거 줄에 나온 세션 이름으로 그 세션에 직접 묻는다(`ListAgents` 로 이름을 확인하고 `SendMessage`).
  예: "#N 을 지금 진행 중인가요? 맡고 있으면 어디까지 했는지 한 줄로 알려 주세요." 답이 올 때까지 그 이슈는
  빼 두고 나머지를 진행한다. 이번 회차 안에 답이 없으면 진행 중으로 보고 보고에 적는다. 다음 회차의 1단계에서
  다시 본다.
- **남은 것 보기**: 남은 worktree·브랜치에 origin/main 에 없는 커밋이 있는가. 그 커밋이 아직 쓸 만한가(이미
  병합된 것과 내용이 같은가). 쓸 만한 준비물이면 계약서에 넣는다(**바로 계약**). 이미 들어갔거나 버려진
  것이면 FREE 로 본다. 남의 worktree·브랜치는 지우지 않고, 보고에서 사람에게 알린다.

### 갈래를 나눈다

| 갈래 | 기준 | 처리 |
|---|---|---|
| **이미 진행 중** | BUSY, 또는 물어서 진행 중이라는 답이 왔다 | 건드리지 않고 보고에 적는다. 본문도 고치지 않는다 |
| **grilling** | 결정이 남아 있거나, 본문이 지금 코드와 어긋났을 수 있다 | 2단계 |
| **바로 계약** | 남은 일이 이미 다 정해졌다(예: PR 은 병합됐고 마무리 한 단계만 남았다) | 남은 일을 확인하고 5단계 |
| **바로 구현** | 이미 `ready-for-agent` 이고, 계약서의 사실 절이 지금 main 과 맞다 | 6단계 |
| **사람 몫** | 사내망·실기기·계정·사람의 판단이 있어야 끝난다 | `ready-for-human` 로 옮긴다. 구현하지 않는다 |

계약서를 쓴 뒤에 그 이슈를 막던 PR 이 병합됐으면, 사실 절(경로·줄 번호·이름·API)을 지금 main 에 대어 본다.
맞으면 사실 절의 `main <sha>` 만 고치고 **바로 구현**으로 둔다. 어긋나면 **grilling** 으로 보낸다.

이번 실행이 맡는 이슈(grilling·바로 계약·바로 구현)는 진행 목록에 넣으며 표시한다. 같은 PC 의 다른
`agent-dispatch` 가 같은 이슈를 집지 않게 하려는 것이다. 표시는 이 세션이 끝나면 저절로 무효가 된다.

```sh
bash "${CLAUDE_PLUGIN_ROOT}/skills/agent-dispatch/scripts/in-flight.sh" --claim --repo <owner>/<repo> <N>...
```

완료 기준: frontier 의 모든 이슈가 다섯 갈래 가운데 하나에 들어갔다. MAYBE 는 답을 받았거나 빼 둔 채 보고 목록에
올랐다. 맡은 이슈는 모두 진행 목록에 들어갔고 표시됐다.

## 서브에이전트의 크기 — model·effort

서브에이전트를 띄울 때마다 그 일의 난이도부터 매기고, 그 등급의 `model`·`effort` 를 Agent 호출에 넣는다.
고르는 기준은 **완료 기준을 한 번에 채울 수 있는 가장 낮은 등급**이다. 모자란 등급으로 돌렸다가 다시 돌리면 처음부터
알맞은 등급으로 돌린 것보다 비싸다.

난이도는 이슈 본문, grilling 리포트, 계약서에서 다음 신호로 읽는다.
- **범위**: 바뀌는 파일·모듈의 수, 호출처가 얼마나 퍼져 있는지, PR 이 몇 개로 나뉘는지.
- **불확실성**: 열린 설계 결정, 원인 모를 결함, 잘 모르는 프레임워크·플랫폼 동작, 동시성·전역 상태·프로세스 경계.
- **위험**: 공개 계약·저장 데이터·보안에 닿는지, 다른 이슈와 계약이 맞물리는지, 회귀를 무엇이 지키는지.

| 등급 | 이런 일 | grilling · 적대적 리뷰 | 구현 |
|---|---|---|---|
| 가벼움 | 판단할 거리가 없는 기계적인 일: 의존성 한 줄, 문구, 이름 바꾸기, 이미 만든 커밋 올리기, 충돌 없는 rebase | `sonnet` · `medium` | `sonnet` · `medium` |
| 보통 | 한 모듈 안의 정해진 변경, 원인이 밝혀진 결함, 시험 더하기, 양쪽 의미를 살려야 하는 충돌 해소 | `sonnet` · `high` | `sonnet` · `medium` |
| 무거움 | 여러 모듈에 걸친 구조 변경, 여러 PR 로 나뉘는 일, 원인 모를 결함, 동시성·상태·프로세스 경계, 다른 이슈와 맞물린 계약 | `opus` · `xhigh` | `opus` · `high` |
| 아주 무거움 | 무거움에 더해, 되돌리기 어렵거나(저장 데이터·공개 계약) 근거끼리 서로 어긋난다 | `opus` · `max` | `opus` · `xhigh` |

- **하한은 `sonnet` · `medium` 이다.** 가벼운 구현도, 사실 하나만 확인하는 작은 조회도 이 크기로 띄운다.
- grilling 은 결정의 근거를 캐고, 적대적 리뷰는 구현자가 놓친 결함을 캔다. 그래서 둘 다 같은 이슈의 구현보다
  effort 가 한 칸 높다. 가벼움만은 모두 하한에 있다. 리뷰어의 크기는 구현의 등급으로 정해 구현 지시문에 넣는다.
- 사용자나 저장소 규칙이 모델·effort 를 정하면 그것을 따른다.
- 정한 등급은 신호 한 줄과 함께 남겨 8단계 보고에 싣는다. 예: "#N 구현 — 무거움: 전역 라우트 이동, PR 6개, 두 조립의 전역 상태".
- **한 칸 올려 다시 보낸다**: 다음 경우에는 같은 등급으로 다시 보내지 않는다.
  - 서브에이전트가 난이도 때문에 멈췄다.
  - 리포트가 3단계 검증에서 틀린 주장을 여럿 냈다.
  - 구현이 완료 기준을 채우지 못했다.
  - 7단계 검수에서 두 번 되돌려 보냈는데도 통과하지 못했다.
- **사람에게 넘긴다**: 다음 경우에는 그 이슈를 `ready-for-human` 으로 옮긴다. 무엇을 해 봤고 어디서 막혔는지
  이슈 댓글로 남기고, 진행 목록에서 빼며 `--release` 한다. 열린 draft PR 은 그대로 두고 보고에 적는다. 이렇게
  끝나는 자리가 있어야 9단계의 루프가 끝난다.
  - 한 칸 올려 다시 보낸 뒤에도 같은 이유로 멈추거나 검수를 통과하지 못했다.
  - 올려야 할 이유가 생겼는데 이미 가장 높은 등급이다.

## 2. grilling 서브에이전트를 보낸다

**grilling** 갈래의 이슈마다 서브에이전트를 하나씩, 한 메시지에서 함께 백그라운드로 띄운다. 읽기만 하는
종류(Plan 등)를 쓴다. 크기는 위 표의 grilling 열로 이슈마다 정해 `model`·`effort` 로 넣는다. 지시문은
[`references/grill-brief.md`](references/grill-brief.md) 를 이슈마다 채워 보낸다. 그 이슈의 설계 문서·ADR·형제
이슈를 이름으로 짚어 줄수록 결과가 좋다.

서브에이전트가 도는 동안 결과에 기대지 않는 일을 바로 한다.
- **바로 계약** 갈래의 남은 일을 실제로 확인한다(그 커밋이 지금 main 위에 그대로 올라가는가 등).
- 리포트와 무관한 사람 질문(환경·정책 같은 것)을 먼저 묻는다.
- 결과가 온 이슈부터 3단계를 시작한다.

완료 기준: grilling 갈래의 이슈마다 리포트가 왔다.

## 3. 리포트를 검증하고 가른다

리포트는 서브에이전트의 주장이다. **결정이 기대는 주장은 네가 직접 확인한다.** 프레임워크 동작, "죽은 코드",
줄 번호·이름이 옮겨 간 것, 시험이 몇 개 깨진다는 것 같은 주장이다. 확인은 코드를 돌리거나 grep 해서 한다.
틀린 주장은 고치고, 그 주장에 기댄 권고는 다시 본다. 틀린 주장이 여럿이면 그 이슈만 한 칸 올린 등급으로 다시
grilling 한다.

묶음 전체를 겹쳐 본다.
- 두 이슈가 같은 파일·같은 계약을 바꾸는가. 그렇다면 순서나 경계를 정한다.
- 한 이슈가 다른 이슈에 기대는데 둘 다 적지 않은 것(**경계**)이 있는가.
- 어느 이슈도 맡지 않은 일이 있는가. 있으면 가장 가까운 이슈에 넣는다(연관된 것은 한 이슈로 묶는다).

열린 질문(OPEN)마다 아래 규칙으로 **정하거나 묻는다**. 정한 것은 근거를 한 줄로 남긴다.

**네가 정한다**
- 이미 기록된 결정이 답한다: 설계 문서, ADR, 지도의 결정 표, 앞선 grilling 의 답.
- 코드·도구의 사실이 답을 강제한다: 다른 선택지가 빌드·시험·런타임에서 깨진다(순환 import, 프레임워크 동작 등).
- 기록된 원칙을 그대로 적용한 결과다: 저장소 `CLAUDE.md`, 사용자의 상시 선호, 용어집의 이름.
- 되돌리기 쉽고 사용자에게 보이지 않는 구현 세부다: 파일 자리, PR 나누기, 시험 하네스.

**사람에게 묻는다**
- 기록된 결정(ADR·지도의 결정·설계 문서의 결정 문장)을 바꾸거나 그 글과 어긋난다.
- 사용자에게 보이는 동작·범위·제품 판단이 갈린다.
- 양쪽에 다 비용이 있는 trade-off 인데, 근거가 어느 쪽도 강제하지 않는다.
- 환경·정책·권한 설정이다: hook, CI, 배포, 외부 서비스, 계정.
- 권고를 받으면 예전에 기각된 안이 되살아난다.

완료 기준: 모든 OPEN 이 "정함(근거)" 이나 "물음" 가운데 하나가 됐다. 결정이 기대는 주장은 모두 직접 확인했다.

## 4. 한 라운드로 묻는다

물을 것을 이슈와 상관없이 한 라운드로 모은다. 번호를 붙이고, 권고를 앞에 둔다. "네"가 권고를 받아들이는 뜻이
되게 쓴다. 각 질문에는 선택지, 권고의 단점, 근거가 답하지 못하는 이유를 함께 적는다.

```
❓ **Q1** - **<질문 제목>**: <배경과 선택지>

➡️ <권고와 그 단점>
```

물을 것이 없으면 이 단계는 건너뛴다. 답이 새 질문을 열면 다음 라운드를 연다. 질문이 걸린 이슈의 단계는 답이 올
때까지 `사람 답` 이다. 그동안 나머지 이슈는 계속 진행한다.

완료 기준: 물은 질문마다 사람의 답이 있다.

## 5. 이슈를 계약서로 다시 쓰고 옮긴다

이슈마다 본문을 다시 쓴다. 본문이 구현 서브에이전트가 받는 **계약서**다. 댓글은 놓치므로 결정은 본문에 넣는다.

본문을 고치기 직전에 그 이슈로 `in-flight.sh` 를 다시 돌린다(근거가 이 실행의 것이면 1단계의 "자기 것 알아보기").
grilling 하는 사이에 다른 세션이 집었으면(BUSY) 본문을 고치지 않는다. 일하는 중인 세션의 계약이 몰래 바뀌기
때문이다. 그때는 정한 것을 그 세션에 메시지로 보내고 보고에 적는다.

본문은 그 저장소 이슈의 언어와 형식을 따르고, 다음을 담는다.

- **선행·상위**: 막는 이슈, 지도, 설계 문서·ADR.
- **사실(`main <sha>` 기준)**: 리포트로 바로잡은 경로·줄 번호·이름. SHA 를 붙여 두어야 나중에 어긋남을 알아본다.
- **할 일**: 정한 것을 단계로 쓴다. 사람이 정한 것은 날짜와 함께 "사용자 결정"으로 적는다.
- **시험**: 결함 수정은 수정 전 커밋에서 빨강, 수정 후 초록. 구조 변경은 회귀를 무엇이 지키는지 적는다.
- **PR**: 몇 개로 나누는지, `Closes`/`Refs`, 시험을 통과한 SHA 를 적는 법, 버전·CHANGELOG 규칙.
- **완료 기준**: 하나씩 확인할 수 있는 것.
- **범위 밖**, 그리고 **경계**: 다른 이슈가 이 이슈에 기대는 것.

그다음 라벨을 옮긴다(`needs-triage` → `ready-for-agent`, 사람 몫은 `ready-for-human`). 진행 목록의 단계는
`ready-for-agent` 면 `구현 대기` 로 바꾸고, 사람 몫이면 진행 목록에서 뺀다. 갈래별 처리:
- **경계**: 기대는 쪽 이슈에 옮긴다. 바로 이어지는 이슈면 본문 절로, 아니면 댓글로.
- **지도**: 결정 표와 "지금 착수할 수 있는 것"을 고친다.
- **사람의 답**: 다음 실행에서도 지켜야 할 것이면 메모리에 남긴다.

완료 기준: frontier 의 모든 이슈가 `ready-for-agent` 나 `ready-for-human` 이다. 경계는 모두 그것을 쓰는 이슈 안에
들어갔다.

## 6. 구현 서브에이전트를 보낸다

대상은 진행 목록에서 단계가 `구현 대기` 인 이슈다. 이번에 `ready-for-agent` 가 된 이슈, **바로 구현** 갈래의 이슈,
앞 회차에 계약을 마치고 겹치는 PR 의 병합을 기다리던 이슈가 여기 있다. 구현 서브에이전트가 붙어 있지 않은
이슈만 이 단계에 있다. 보내면 단계를 `구현` 으로 바꾸고 agent id 를 적는다.

**보내기 직전에 대상 전부로 `in-flight.sh` 를 다시 돌린다.** grilling·질문을 하는 동안 다른 세션이 집었을 수 있다.
- **보낸다**: FREE, 근거가 "claim: 이 세션" 뿐인 것, 또는 근거가 이 실행의 것인 것(1단계의 "자기 것 알아보기").
- **보내지 않는다**: 다른 세션 때문에 BUSY 인 것. 다른 세션 때문에 MAYBE·HELD 인 것은 1단계처럼 다룬다.

서브에이전트의 worktree 디렉터리와 브랜치 이름에는 이슈 번호를 넣는다. 다른 세션의 `in-flight.sh` 가 그것으로
진행 중을 알아본다.

- **종류로 절차를 고른다**: `bug` 라벨이면 `diagnosing-bugs`, 그 밖(기능·리팩터·시험·문서)이면 구현 절차다.
  지시문은 [`references/implement-brief.md`](references/implement-brief.md) 를 이슈마다 채워 보낸다.
- **리뷰어 지시문을 넣는다**: [`references/review-brief.md`](references/review-brief.md) 를 그 이슈로 다 채워
  구현 지시문의 리뷰 단계 자리에 넣는다. 서브에이전트는 이것을 그대로 리뷰어에게 넘긴다. 리뷰어의 `model`·`effort`
  도 지시문에 적는다(크기 표의 "grilling · 적대적 리뷰" 열).
- **크기를 정한다**: "서브에이전트의 크기" 표의 구현 열로 이슈마다 `model`·`effort` 를 정해 넣는다. 계약서가
  확정된 뒤라 grilling 때보다 불확실성이 줄었다. 그래서 grilling 때의 등급을 그대로 가져오지 않고 계약서를 보고
  다시 매긴다. 원인이 계약서에 밝혀지지 않은 결함은 무거움 이상이다.
- **같이 돌릴지 정한다**: 계약서가 바꾸는 파일이 겹치지 않으면 한 메시지에서 함께 백그라운드로 띄운다. 겹치면
  둘 가운데 하나를 고른다.
  - 함께 보내고, 겹침을 지시문에 적어 rebase 를 예고한다.
  - 먼저 병합될 것부터 보낸다. 뒤로 미룬 이슈는 `구현 대기` 에 두고 어느 PR 의 병합을 기다리는지 적는다. 그 PR 이
    병합된 뒤의 6단계에서 보낸다. 기다리는 PR 이 열려 있는 동안에는 보내지 않는다.
- **서브에이전트마다 자기 worktree 를 쓴다**: 저장소 규칙이 정한 자리에, 이슈 번호가 든 이름으로 만든다.
- **이미 있는 PR·worktree 를 맡기면 이어 하기로 보낸다**: 그 이슈를 맡은 서브에이전트에게는 `SendMessage` 로
  후속 요청(Fix · Rebase · Next PR, 구현 지시문의 "Follow-up requests")을 보낸다. 새로 띄워야 하는 경우는 셋이다.
  - 원래 서브에이전트가 없다(세션이 바뀌었다 등).
  - 등급을 올려야 한다. `SendMessage` 로는 `model`·`effort` 를 바꿀 수 없다.
  - 후속 요청의 등급이 원래 등급보다 높다(의미를 살려야 하는 충돌 등).

  새로 띄울 때는 구현 지시문의 이어 하기 줄에 그 PR·브랜치·worktree 와 요청을 채워 보낸다. 그래야 두 번째
  worktree·PR 이 생기지 않는다. 7·9단계의 "이어 하기"는 모두 이 규칙을 따른다.

리포트가 오는 대로 그 PR 을 7단계로 검수한다. 나머지 서브에이전트를 다 기다리지 않는다.
- 서브에이전트가 계약서의 빈틈으로 멈췄으면, 그 빈틈을 3·4단계로 메우고 계약서를 고친 뒤 다시 보낸다.
- 난이도 때문에 멈췄으면 한 칸 올려 다시 보낸다.

완료 기준: 보낸 서브에이전트마다 PR(또는 계약서가 정한 마무리)과 시험 통과 SHA 가 있거나, 멈춘 이유와 다음
조치가 있다.

## 7. PR 을 최종 검수한다

서브에이전트의 리포트와 PR 본문은 주장이다. 사람에게 넘기기 전에 **PR 마다 직접 확인한다.** 서브에이전트는 PR 을
draft 로 열어 넘긴다. 검수를 통과해야 네가 ready 로 바꾼다. 검수하는 동안 단계는 `검수` 다.

확인은 그 PR 의 worktree 에서 PR HEAD 그대로 한다. 다른 커밋을 돌려 봐야 하면 임시 사본에서 한다
(`git worktree add --detach <임시 경로> <커밋>`, 끝나면 지운다). 서브에이전트의 worktree 는 HEAD 와 작업 트리를
그대로 둔다. 되돌려 보내면 서브에이전트가 그 자리에서 이어 일하기 때문이다. draft 를 쓸 수 없던 PR 이 검수 전에
병합됐으면, 검수를 마저 하고 걸린 것은 후속 이슈로 낸다. 그다음 9단계의 `MERGED` 처리를 한다.

1. **모양**: 시험을 돌리기 전에 본다. 아래가 모두 맞아야 한다.
   - PR 이 열려 있고 base 가 맞다.
   - PR HEAD(`gh pr view --json headRefOid`)가 그 PR 브랜치의 로컬 HEAD 와 같고, 리포트의 시험 SHA 와도 같다.
   - 작업 트리가 깨끗하다.
   - base 와 충돌하지 않는다(`mergeable` 이 `MERGEABLE`). `UNKNOWN` 은 GitHub 가 계산하는 중이니 잠시 뒤 다시
     조회한다.
2. **시험을 다시 돌린다**: 계약서의 시험 명령을 PR HEAD 에서 직접 돌린다. 리포트의 숫자를 옮겨 적지 않는다.
   같은 트리를 쓰는 명령끼리는 동시에 돌리지 않는다. 시험이 작업 트리에 산출물을 남기는 저장소면 임시 사본에서
   돌린다.
3. **계약 대조**: diff 를 계약서와 맞춘다.
   - 할 일과 정한 것이 모두 들어갔는가. 범위 밖 변경이 없는가.
   - 계약서가 막은 것(다른 이슈가 맡은 파일, 버전·CHANGELOG 규칙)을 건드리지 않았는가.
   - 바뀐 기존 단언마다 계약서의 예외이거나 이유가 적혀 있는가.
4. **주장을 재현한다**: 리포트의 주장 가운데 결과를 좌우하는 것을 하나 이상 임시 사본에서 직접 재현한다. 예:
   - "리팩터 커밋에서 기존 시험이 그대로 통과한다" → base 의 시험 파일을 그 커밋에 얹어 돌린다.
   - "수정 전에는 빨강이다" → 수정 전 커밋에서 그 시험을 돌린다.
5. **완료 기준의 체크**: 이슈 본문에서 체크된 기준마다 실제로 채워졌는가를 본다. 일부만 채운 것이 체크돼 있으면
   체크를 풀고 이유를 댓글로 남긴다.
6. **리뷰 기록**: 리포트의 리뷰 표를 본다.
   - 기각·미룸 항목마다 판단한다. 동의하지 않는 것은 되돌려 보낸다.
   - 리뷰 표가 빠졌으면 네가 리뷰어를 띄운다. 서브에이전트가 리뷰어를 띄우지 못한 경우, 마지막 리뷰 뒤에 동작을
     바꾼 커밋(수정·의미를 살린 충돌 해소)이 있는 경우가 그렇다. 지시문은
     [`references/review-brief.md`](references/review-brief.md), 크기는 크기 표의 "grilling · 적대적 리뷰" 열이다.
     이 리뷰는 한 PR 에 두 라운드까지 하고, 라운드 수는 진행 목록에 센다.
   - 되돌려 보내는 것은 `blocker`·`major` 뿐이다. `minor` 는 보고와 PR 본문의 후속으로 남긴다.
7. **계약과 다른 점**: 하나씩 받아들일지 정한다. 받아들인 것은 계약서(이슈 본문)에도 반영한다. 다음 회차가 그
   계약서를 사실로 읽기 때문이다.

**통과**:
1. `gh pr ready` 로 ready 로 바꾼다. draft 를 쓸 수 없어 본문 첫 줄에 경고를 둔 PR 이면 그 줄을 지운다.
2. 단계를 `병합 대기` 로 바꾼다.
3. 지켜보기 목록에 넣고 지켜보기를 다시 건다(9단계).

**걸림**:
1. 단계를 `수정` 으로 바꾼다.
2. 그 서브에이전트에게 Fix 요청을 보낸다(6단계의 이어 하기 규칙).
3. 고쳐 오면 이 단계를 처음부터 다시 한다.

되돌린 횟수는 진행 목록에 센다. 사람이 PR 에서 요청한 수정은 세지 않는다. 두 번 되돌려도 통과하지 못하면
"서브에이전트의 크기"의 "한 칸 올려 다시 보낸다"·"사람에게 넘긴다"를 따른다.

완료 기준: PR 마다 다음 가운데 하나다.
- 일곱 항목을 통과해 ready 가 됐다. 다시 돌린 시험 결과와 재현한 주장이 보고에 실을 만큼 남았다.
- 되돌려 보낸 이유와 다음 조치가 있다.

## 8. 보고한다

검수를 통과한 PR 이 생길 때마다, 그리고 회차가 끝날 때마다 사람에게 짧게 보고한다.
- 이슈마다 상태 한 줄: 갈래, 라벨, PR, 시험 SHA, 서브에이전트의 등급(`model`·`effort`, 올렸으면 그 이유).
- 검수 결과: 다시 돌린 시험, 재현한 주장, 되돌려 보낸 것과 그 결말. 리뷰 표에서 기각한 것 가운데 판단이 들어간 것.
- 네가 정한 것 가운데 판단이 들어간 것.
- 병합 순서처럼 사람이 알아야 할 위험.
- 병합 뒤 다음 frontier 로 풀리는 이슈.
- 진행 중이라 건너뛴 이슈와 그 세션 이름. 주인 없이 남은 worktree·브랜치도 적는다.

표시(claim)는 1단계 규칙대로 진행 목록에서 뺄 때 거둔다.

**상태 블록**: 맥락이 요약되면 대화에서 기억할 수 있는 것은 이 블록뿐이다. 이 블록만으로 회차를 이어 가고 상한을
지킬 수 있게 빠짐없이 적는다. 보고 끝에 두고, 그 사이에도 진행 목록이나 지켜보기가 바뀔 때마다 다시 낸다.

```
지도 #<M> · 회차 <k> · 라벨 <needs-triage>/<ready-for-agent>/<ready-for-human> · 원칙 <0단계에서 정한 것 한 줄>
지켜보기: task <id> — 이 실행의 PR #<a> #<b> · 남의 PR #<c>      (없으면 "없음")
처리한 병합·닫힘: #<p> #<q>
진행 목록:
  #<x> grilling · agent <id>
  #<y> 사람 답 · Q<번호>
  #<z> 수정 · agent <id> · <등급>(올림 <0|1>) · 되돌림 <n>/2 · 리뷰 라운드 <n>/2 · worktree <경로> · PR #<d>(draft)
  #<w> 구현 대기 · PR #<e> 병합을 기다림
물어 둔 세션: #<n> → <세션 이름>
병합 뒤 풀리는 이슈: #<u> #<v>
```

## 9. 병합을 기다리고 다음 frontier 로 이어 간다

PR 의 병합은 사람이 저장소의 리뷰·병합 절차로 한다. 너는 병합하지 않는다. 병합을 지켜보다가 그 뒤의 일을 한다.

**회차**: 처음 부른 것이 1회차다. 이후 지켜보던 PR 이 병합되거나 닫힐 때마다 1단계로 돌아가며 새 회차를 연다.
- 고를 frontier 가 없으면 2~5단계를 건너뛰고 6단계로 간다. 진행 목록의 `구현 대기` 이슈를 보내야 한다.
- 같은 묶음의 다른 PR 이 아직 열려 있어도, 풀린 이슈는 바로 진행한다.

**지켜보기 목록**은 둘이다.
- **이 실행의 PR**: 단계가 `병합 대기` 인 PR. draft 이거나 검수·수정·rebase 중인 PR 은 넣지 않는다. 그런 PR 은
  7단계를 통과하면 들어온다. 충돌이 남은 PR 을 넣어 두면 지켜보기가 곧바로 다시 깨어난다.
- **남의 PR**: 지도 안의 남은 이슈를 막고 있는데 다른 세션이 연 열린 PR. 그 병합이 다음 frontier 를 연다.

**지켜보기를 건다**: Bash 의 `run_in_background` 로 띄우고, 그 task id 를 상태 블록에 적는다.

```sh
bash "${CLAUDE_PLUGIN_ROOT}/skills/agent-dispatch/scripts/wait-prs.sh" --repo <owner>/<repo> \
  [--other <남의 PR>]... <이 실행의 PR>...
```

- 스크립트는 그 회차에 일이 생긴 PR 을 모두 출력하고 끝난다. 끝나면 harness 가 너를 다시 부른다. 그사이 따로
  폴링하지 않는다.
- **스크립트는 한 번 깨어나면 끝난다.** 일을 처리할 때는 맨 먼저, 1단계로 가기 전에 다시 건다. 병합되거나 닫힌
  PR 은 목록에서 뺀다. 그래야 사람 답을 기다리는 회차 동안에도 다른 PR 을 계속 지켜본다. 두 목록이 다 비었으면
  걸지 않는다.
- 지켜보기는 하나만 둔다. 목록이 바뀌면(검수를 통과한 PR 이 생기는 등) 지금 것을 `TaskStop` 으로 멈추고 새
  목록으로 다시 건다. 멈춘 task 의 완료 알림은 무시한다.
- 사람이 먼저 알려 오면("merged"·"conflict"·"PR 에 수정 요청 남겼어") 지켜보기를 멈추고 같은 처리를 한다. 수정
  요청은 그 리뷰 댓글을 서브에이전트에게 Fix 로 넘긴다. 그동안 그 PR 은 목록에서 빼고, 7단계로 다시 검수한다.
- 일은 PR 마다 한 번만 처리한다. "처리한 병합·닫힘"에 있는 PR 의 일이 다시 오면 건너뛴다.
- 백그라운드 실행을 쓸 수 없는 환경이면 상태 블록을 남기고 사람의 병합 소식을 기다린다.

**일마다 처리한다**:

- **`MERGED` — 이 실행의 PR**
  1. 지켜보기를 다시 걸고, "처리한 병합·닫힘"에 적는다.
  2. 이슈가 닫혔으면 저장소 규칙대로 그 worktree·브랜치를 지우고, 진행 목록에서 빼며 `--release` 한다.
  3. 이슈가 열려 있고 계약서에 남은 PR 이 있으면 worktree 는 남긴다. 단계를 `다음 PR 대기` 로 바꾸고 Next PR
     요청을 보낸다(6단계의 이어 하기 규칙). 남은 PR 이 없는데 이슈가 열려 있으면 완료 기준을 확인해 닫거나 사람에게
     알린다.
  4. 남은 `병합 대기` PR 가운데 같은 파일·계약에 닿는 것은 임시 사본에서 새 base 위로 올려 시험을 다시 돌린다.
     깨지면 그 PR 을 목록에서 빼고 Fix 로 되돌려 보낸다. 텍스트 충돌 없이 깨지는 의미 충돌을 잡으려는 것이다.
  5. 1단계로 돌아간다. 이 병합으로 풀린 이슈가 frontier 에 들어온다.
- **`MERGED`·`CLOSED` — 남의 PR**: 지켜보기를 다시 걸고, "처리한 병합·닫힘"에 적은 뒤 1단계로 돌아간다.
- **`CONFLICTING`**(이 실행의 PR 만 나온다)
  1. 그 PR 을 목록에서 빼고 지켜보기를 다시 건다.
  2. 단계를 `rebase` 로 바꾸고 Rebase 요청을 보낸다(6단계의 이어 하기 규칙). 충돌의 성격으로 등급을 매긴다.
  3. 끝나면 7단계로 다시 검수한다. rebase 가 사람 판단에 걸려 멈추면 4단계로 묻고, 답이 올 때까지 목록 밖에 둔다.
- **`CLOSED` — 이 실행의 PR**: 병합 없이 닫혔다.
  1. 지켜보기를 다시 걸고, 단계를 `사람 답` 으로 바꾼다.
  2. 사람에게 이유를 묻는다. 답에 따라 5단계로 다시 계약하거나 지도에서 뺀다.
- **`GH_FAILING`**: 그 줄의 이유를 본다.
  - 번호가 틀렸거나 지워진 PR 이면 목록에서 고쳐 다시 건다.
  - 인증·네트워크 문제면 사람에게 알리고, `--interval 300` 으로 늘려 다시 건다.
- **`TIMEOUT`**: `--timeout` 을 준 경우에만 나온다. 다시 건다.
- **exit 2**: 인자가 틀렸다. 고쳐 다시 건다.

**끝낸다**: 다음이 모두 참이면 마지막 보고를 하고 멈춘다.
- 진행 목록이 비었다.
- 지켜볼 PR 이 두 목록 모두 없다.
- 1단계에서 고를 frontier 가 없다.

이때 남은 하위 이슈는 닫혔거나, 사람 몫이거나, PR 없이 다른 세션이 쥐고 있거나, 그런 이슈 또는 지도 밖의 이슈에
막혀 있다. 깨울 사건이 없으니 기다리지 않는다. 막힌 것이 풀리면 사람이 다시 부른다.

사람이 멈추라고 하면 그 자리에서 지켜보기를 멈추고 보고한다. 마지막 보고에는 지도 전체의 상태를 싣는다.
- 닫힌 이슈와 그 PR.
- 남은 이슈와 남은 이유. 사람이 풀어야 다시 돌 수 있는 것을 먼저 적는다.
- 정리한 worktree. 주인 없이 남은 worktree·브랜치.

완료 기준: 다음 가운데 하나다.
- 지켜보기가 걸려 있고, 상태 블록이 그 task·PR 을 적는다.
- 사람 답을 기다리는 질문만 남았고, 상태 블록이 그것을 적는다.
- 끝낼 조건이 참이라 마지막 보고를 했다.
